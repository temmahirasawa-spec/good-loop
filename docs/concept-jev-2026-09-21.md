# 1. 結論 ── GOOD REVIEW は何になるべきか

> ## **GOOD REVIEW は「クチコミを増やす道具」をやめ、「あなたの店が、いま第三者にどう読まれていて、どの声ならまだ間に合うかを、毎日、同じ目盛りで測る計器」になるべきです。**

**旗の一行を、こう入れ替えます。**

| | いま | これから |
|---|---|---|
| 旗 | 「AIは書きません。あなたが書きます。」 | **「AIは書きません。測ります。」** |

前半（AIは書きません）は**1文字も変えません**。v4 で決めた背骨はそのままです。
変えるのは後半です。いままでは「書かない」の**あとが空白**でした。だから「AIを使わない製品」に見えて、
天真さんが感じたとおり「泥臭い戦い」の土俵に降ろされていました。

**そこに「測ります」を入れると、AIを使う理由が製品の中心に戻ってきます。**
しかも Jev は**構造的に文字を書けない**ので、この一行は「方針の表明」ではなく**そのAIの性質そのもの**になります。

**製品名は変えません。** GOODシリーズの統一（GOOD LOOP / GOOD ORDER）と、
すでにドメイン・Stripe・契約が動いていることを考えると、改名はコストだけがかかって効果が薄いからです。
変えるべきは名前ではなく、**何を測る会社か**です。

# 2. なぜいま変えるのか ── 制約がAIを殺したのではない。置き場所を間違えていた

## 2-1. 事実の確認

これまで、GOOD REVIEW が AI を置いてきた場所は**たった1箇所**です。
**「来店客がGoogleに出す文章」** ── つまり、規約が唯一はっきり縛っている、その場所です。

そこに置いたので、何が起きたか。

- 全文生成をやめ（v4）、**AIが出せるのは助詞と句読点だけ**になった
- それでも足りず、サーバー側に検査層（`lib/survey/polish-guard.ts`、289行）を作った
- その検査層を破りにいくレビューをかけたら、**18件の実害**が出た。1件ずつ塞いで回帰テストに固定した

**エンジニアリングの力のほとんどを、AIを縛る檻を作ることに使ってきました。** そして檻は正しい。
やめるべきではありません。ただ、**檻を作ることは、価値を作ることではありません。**

一方で、**規約が何も縛っていない場所が3つ、ほぼ手つかずで残っています。**

| 場所 | 規約は何と言っているか | いま何が置いてあるか |
|---|---|---|
| **店舗の画面・分析・通知** | 何も言っていない（Googleのポリシーも景表法も、来店客の投稿についての話） | ★の平均と件数だけ。AIはゼロ |
| **お店に直接届く声**（Googleに出さない声） | 内容への影響の禁止はかからない（公開される表示ではない） | そのまま保存するだけ。AIはゼロ |
| **店の評判が動いている外の世界**（自店のGoogleページ、いまそこにある数百件の日本語） | 自店のプロフィールなので自由に読める | **1件も読んでいない** |

**「制約があるからAIが使えない」は誤解でした。正しくは「Googleに出す文章の生成にだけ使えない」です。**
そして私たちは、その唯一使えない場所にだけ AI を置き、残りの広大な場所を空けたまま
「AIを使うアイデアが出ない」と言っていた、というのが実態です。

## 2-2. Jev の何がそれを変えるのか

天真さんが見つけたゲーム開発者の観察 ── 「Jevで感情とトピックを判定していて、全然お金がかからない」 ──
の本質は、新しい機能ではありません。**AIの置き場所が「節目」から「環境」へ移ったこと**です。

従来のAIは高くて遅いので、**送信ボタンを押した瞬間にしか呼べませんでした。**
Jev は 70〜500ms・入力 $0.042/MTok・**出力は無料**なので、**常時、全件、毎日**呼べます
（出典: `docs/handoff-jev-2026-09-21.md` §6-1。Cloudflare Workers AI の `typesafe/jev` 経由で今すぐ使える／付録A-1）。

そしてもう1つ、より重要な性質があります。

> **Jev が返すのは「較正された確率」です。**
> 較正（きょうせい）＝「0.8 と言ったものは、10回のうち8回くらい当たる」が実際に成り立っていること。
> ふつうのAIの「自信あります」は当てになりませんが、Jev はそこを目的に学習していると公表されています。

**計器に必要なのは、正解ではなく目盛りです。**
毎回同じ物差しで測れて、足し算ができて、去年と比べられる ── それが「測る」ということで、
文章を生成するAIには原理的にできません（呼ぶたびに出力が揺れ、プロンプトを直した瞬間に過去と比較できなくなる）。

**書けないことは制限ではなく、「測る係」に徹しているという保証です。**
そして GOOD REVIEW が v4 で選んだ「AIは書かない」と、Jev の「書けない」は、偶然ではなく同じ方向を向いています。

# 3. 本命の構想（3つ）

順番には意味があります。**1が入口（売れ始めるため）、2が定着（解約されないため）、3が堀（群を抜くため）**です。

---

## 【本命1】読まれ方（YOMARE-KATA）── あなたの店は、いま第三者にどう説明されているか

**一文の定義**

> **クチコミを1件ずつ読むのをやめ、「クチコミの束が、第三者に要約されたあと何が残るか」と
> 「読者から代筆を疑われる特徴がどれだけ混ざっているか」を、同じ目盛りで毎月測って店に返す診断。**

### 3-1-1. 何が決定的に変わるか

いま店主は、自分のクチコミを1件ずつ見ます。**しかし、来店を検討している人は1件ずつ読みません。**
地図アプリのAI要約を読み、検索結果のAI要約を読み、上から3件だけ読みます。

> **つまり、店の評判の実体は「個々のレビュー」ではなく「要約されたあとに残るもの」です。**

ここを測っている製品は、調べた範囲では国内にも海外にも見当たりませんでした
（※「見つからなかった」は「存在しない」の証明ではありません）。
海外最大手 Birdeye がやっているのは「トピック分析」と「競合比較」で、**読まれ方ではありません。**

そして、この診断は**同じ貼り付け1回から、もう2つの読み方**を出します。

| 何を出すか | 読み方 |
|---|---|
| **① 読まれ方（攻め）** | 「あなたの店は『安い』『待つ』の店として読まれます。『技術が丁寧』は12件に書かれていますが、短く要約すると残りません」 |
| **② 疑われ度（守り）** | 「43件のうち17件に、読者から代筆を疑われやすい特徴があります」 |
| **③ 迷いの地図（構造）** | 「あなたの店で最も分離できない2つ：清潔さ と 混雑。＝混んでいるときだけ汚く見えています」 |

③は説明が要ります。**分類は、確率を1つのラベルに潰す操作です。潰した瞬間に消える情報のほうに価値があります。**
Jev が繰り返し「待ち時間0.48／接客0.46」で割れる店は、分類の失敗ではなく、
**その店では待ち時間の不満が接客の不満として語られている**という発見です。打つ手が変わります
（回転率ではなく、待たせている間の声かけ）。
競合はハードなラベル（1つに決めた答え）しか持っていないので、**この情報は原理的に取れません。**

### 3-1-2. 画面と体験

**店舗側（これが主役。来店客の画面には1ピクセルも出ません）**

1. 既存の「AI視認性チェッカー」の入れ物（`components/ai-check/` 一式、`/api/checker/ask`）をそのまま使います
2. 店主が、自分のGoogleビジネスプロフィールを開いて、**自店のクチコミを選択してコピーし、貼り付ける**
   （※Google連携のログイン＝OAuth も、Googleへの利用申請も要りません。§3-1-6 で理由を書きます）
3. 30秒ほどで結果が出る

**画面に出る文言（案）**

```
御社のクチコミ 83件を読みました。

■ いま、こう説明されます
　「安い」「待つ」の店

■ 伝わっていない体験
　技術が丁寧 …… 12件に書かれています。
　　　　　　　　　短く要約したとき、残る確率 0.18（同業態の中央値 0.44）
　　　　　　　　　※ 12件が他の話題と混ざった長文の中にあるためです

■ 読者から疑われやすい特徴
　83件のうち 17件
　（定型の型にはまった書き方 11件／他の投稿と骨格が似すぎ 9件 ※重複あり）

■ お客様の中で一緒になっているもの
　清潔さ と 混雑（同居 0.61 ／ 同業態 0.22）
　→ 掃除が足りないのではなく、混んでいるときだけ汚く見えています
```

**⚠ 画面に絶対に出さないもの（条文として仕様に書きます）**

- **「どう書いてもらうか」の助言を1文字も出しません。** 出すのは「どの体験が伝わっていないか」まで。
  「具体的に書いてもらいましょう」「長めに書いてもらいましょう」は、すべて**Googleポリシー層2への直行便**です
- **「偽物です」と断定しません。** 当社は事実を知りません。言えるのは「疑われやすい特徴があります」まで
- **消すことを勧めません。** 数字を出すだけで、次の行動を指示しません
- **他店を採点しません。** オーナー権限で確認できる自店のみ

**来店客側：何も変わりません。** この構想は来店客の画面に一切出ません。

### 3-1-3. Jev に何を入れ、どんな型の何を返させるか

Jev の問いは **choice / noul / score の3種類だけ**で、**1問＝1つの値**です。
そして**1回のリクエストに何十問でも束ねられます**（出典: handoff 付録A-2）。
以下はすべてその形に収まります（＝可変長の配列を返させる設計ではないので、実際のAPIで書けます）。

**パスA（1件ずつ。全レビューに1回）**

```
state = { text: レビュー本文1件, business_category: 業態, peer_skeleton: 同一店の直近レビューの骨格 }

questions（1リクエストに束ねる）:
  axis_food      : noul  { true: "料理・品そのものに触れている",   false: "触れていない" }
  axis_wait      : noul  { true: "待ち時間に触れている",           false: "触れていない" }
  axis_service   : noul  { true: "接客の場面に触れている",         false: "触れていない" }
  axis_clean     : noul  { true: "清潔さに触れている",             false: "触れていない" }
  axis_price     : noul  { true: "価格の納得に触れている",         false: "触れていない" }
  axis_space     : noul  { true: "席と空間に触れている",           false: "触れていない" }
  …（体験の軸ぶん。12軸程度）

  template_like  : noul  { true: "定型の型にはまった書き方",       false: "その人の書き方" }
  generic_praise : noul  { true: "具体的な出来事がなく評価語だけ", false: "出来事がある" }
  peer_similar   : noul  { true: "同じ店の他の投稿と骨格が似すぎ", false: "似ていない" }
  too_short      : noul  { true: "判断材料が足りないほど短い",     false: "足りている" }
```

**パスB（店ごと1回。束を丸ごと入れる）**

```
state = { reviews: 貼り付けたクチコミの束（32,000トークンに収まる単位）, business_category }

questions:
  survive_food    : score ["この店の説明に出てこない", "触れられている", "この店の説明の中心"]
  survive_wait    : score [ 同上 ]
  survive_service : score [ 同上 ]
  …（パスAと同じ12軸）
```

**文字列は1つも返させません。** 返るのは軸ごとの確率と段階だけです。

**③迷いの地図には、Jev の追加の呼び出しは要りません。**
パスAの確率を**ラベルに潰さずそのまま保存**して、(i) 1件ごとの割れ具合 (ii) 軸ペアの同居確率
を集計するだけです。`too_short` は「本当に混ざっている」と「短くて情報がない」を分けるために要ります。
区別できないときは、その軸ペアを画面に出しません。

### 3-1-4. Jev が外したときに何が起きるか

**外しても害が出ない置き場所です。** 理由を3つ。

1. **来店客の画面に一切出ません。** 判定結果が投稿導線に到達する経路がコード上に存在しません
   （＝規約リスクの経路が物理的にない）
2. **1件の判定がずれても、83件の集計の中では数字が0.01動くだけ**です。統計に沈みます
3. **「17件」のような数を言い切れるのは較正のおかげ**で、ここが外れると数字がずれます。
   だから**§5-1 の日本語の実測を、実装より先にやる**ことを着手条件にします

**Jev が使えないとき（落ちている・429が返る・日本語が効かない）の退避：**
診断そのものを出さず、「いまは診断できません」とだけ出します。**壊れた数字を出すより出さないほうが良い**種類の機能です。
これは既存の検査層の思想（落ちたら何も出さない）と同じです。

### 3-1-5. なぜ競合が真似できないか

**非対称が本物です。**

国内競合5社（Revimy／キキコミ／AskTap／MEO CHEKI REVIEW byGMO／口コミロボ）は、
**全社が「AIが文章を書きます」を主訴求にしています**（`docs/strategy-2026-09-13.md` §3-1）。

この診断を彼らが出すと、**自社の出力が「疑われやすい」「要約に残らない」と採点される**ことになります。
**自社の看板が、そのまま参入障壁になっている構造**です。

加えて、**FROMA で第三者から「ステマをやっている」と実際に書かれた経験を持っているのは UTUTU だけ**です。
その傷が、そのまま営業の説得力になります。

正直に書くと：**技術としては半年〜1年で追いつけます。** Jev は誰でも契約できます。
真似しにくいのは技術ではなく**立場**で、そこは時間ではなく製品定義の転換が要ります。

### 3-1-6. 規約・法令の判定

| 条項 | なぜ安全か |
|---|---|
| **Google 層1（gating）** | 来店客の画面に一切出ない。届け先の出し方・順番・大きさ・文言に到達する経路がない |
| **Google 層2（内容への影響）** | 投稿前の来店客に何も提示しない。出力の型に「文面に関する助言」を1つも置かない（§3-1-2の条文） |
| **景表法（ステマ規制）** | 来店客との間で投稿内容についての情報のやり取りが発生しない。AIが文章を1文字も作らないので、**店が責任を負う新しい表示が1文も生まれない** |
| **見返り** | 無関係 |
| **スタッフ別ランキング** | 軸にスタッフ個人を置かない（v4 §9 と同じ条文を適用） |

**⚠ 危ないところを自分から書きます。**

1. **いちばん危ないのは「要約に残る書き方」に転ぶ誘惑です。** 「こう書いてもらえば残ります」を1行でも出した瞬間に、
   これは層2への直行便になり、製品の思想も殺します。**出力の型に助言を置かない**を条文で縛ります
2. **Googleからの取り込み方。** スクレイピング（画面から機械で抜くこと）は使いません。
   Google Business Profile API も**使いません**（オーナーのログイン連携＝OAuth の仕組みがこのリポジトリに1行も無く、
   Googleへの利用申請と審査が別途かかるため。実装審査の指摘）。
   **店主が自分のクチコミを貼り付ける形**にします。これで技術的にも規約的にも論点が消えます
3. **本文をサーバーに保存しません。** Jev に通して**確率だけ残し、本文は捨てます**。
   これで「取得したレビュー本文の保存・再表示」という論点そのものが立たなくなります
4. **投稿者名を取り込みません。** 列をスキーマに作りません（作れないようにします）。
   handoff §5-1 が「資産」と書いた匿名性を、この機能で壊さないためです
5. **外部へ送るので、委託先の記載が要ります。** ただし「表に1行足せば済む」ではありません。**§5-3 を必ず読んでください**

### 3-1-7. 工数と、いつ出せるか

**7人日。** 内訳：精度の実測2日（§5-1）／採点3日／画面・文言2日。
入れ物（`components/ai-check/` 一式）が既にあるので、中身の差し替えで済みます。

**10月中に出せます。** ただし**リリースA（§6）の後**です。

### 3-1-8. 誰がいくら払うか

- **診断そのものは無料。** 見込み客を集める入口です。LPがまだ無い現在でも、**営業の持ち物**として今日から使えます
- **払うのはそこから契約する店舗**で、月9,800円。値上げはしません（§6-4 に理由）
- **契約後は「毎月の推移」として続きます。** 「先月より『技術が丁寧』が残る確率が 0.18 → 0.26 に上がりました」。
  これが管理画面を開く理由になります

**営業の一行が変わります。**

| | |
|---|---|
| いま | 「口コミが増えます」（競合5社と同じ言葉） |
| これから | **「あなたの店が、いまどう説明されているかを出します。無料です。」** |

## 【本命2】取り返し時計 ── 「何を直すか」ではなく「いつまでなら直せるか」で仕分ける

**一文の定義**

> **店に届いた声を「いま直せる／この来店中なら／今日なら／構造的に今日は直せない」の4つに型で仕分けて、
> 行動が残っているものだけを店長に鳴らす通知。**

（構想[9]を軸に、[14]「90秒の店長」と[32]「境界宣言」を統合した1本です。3つとも中身がほぼ同じでした）

### 3-2-1. 何が決定的に変わるか

いまの低評価アラート（`lib/rating-flow/low-rating-alert.ts`、`LOW_RATING_THRESHOLD = 3`）は
**「★2が来ました」と言うだけ**です。読んだ店長にできることが何もないので、**数週間で通知を切られます。**

取り返し時計は**行動が残っているものだけ**を鳴らします。
逆に「設備・立地・価格」のような今日は直せないものは鳴らさず、月次にまとめます。

> **鳴る回数が減って、鳴ったら必ず動く通知になります。**

そして、直せた不満は**そもそもGoogleに書かれません。** ただし**書かせないようにしたわけではありません。**
届け先も、順番も、文言も1ミリも触っていない。**店が実際に良くなっただけ**です。
合言葉「これはハックか、適正化か」に対する、いちばん明快な答えがこれです。

競合B群（Surveyprime・マイビジレビュー）が「低評価を店内に留める」で売っているものを、
**留めるのではなく消す**という、まったく別の売り方に置き換えられます。

### 3-2-2. 画面と体験

**店舗側**

届いた瞬間（0.5秒以内）にメールが飛びます（既存の Resend 通知にそのまま乗ります）。

```

19:05 に届きました。

　お客様の言葉：
　「予約してたのに席案内おそい」

　だれが　　　　　： ホール
　かかるもの　　　： 数分でできること
```

**⚠ この画面に絶対に置かないもの（条文）**

- **Googleへの導線**
- **投稿依頼の文言**
- **レビューの件数**

理由：「いま直せる人に声をかけてGoogleに書いてもらおう」という運用が現場で生まれた瞬間に、
それは**選択的な募集そのもの（層1に直撃）**になります。**製品側で芽を摘みます。**
オンボーディングの文書にも「この画面を見て来店客に投稿を頼まないこと」を条文として書きます。

**来店客側：何も変わりません。**

### 3-2-3. Jev に何を入れ、どんな型の何を返させるか

### 3-2-4. Jev が外したときに何が起きるか

**37件で最も害が軽い置き場所です。**

- 直せないものが1件混ざる → 無視すればよい
- 直せるものを1件見逃す → **現状は全部見逃しているので、悪化しません**

**退避（これが大事）：**

「Jevが無いと壊れる」状態になりません。

### 3-2-5. なぜ競合が真似できないか

**正直に書きます。機能そのものは真似できます。** カンリーは既に口コミの即時通知を売っており、
緊急度の分類は任意のLLMでも作れます（遅くて高いだけ）。

真似できないのは**入口のデータ**です。競合が持っているのは**レビュー本文だけ**で、
それは `structural`（設備）と `this_visit`（いま直せる）が既に混ざって固まったあとの物体です。
**そこから時間の窓を復元することはできません。**
GOOD REVIEW は「Googleに出す前の声」「そもそもGoogleに出さない声」を持っています。
**機能を真似しても、同じ画面にはなりません。**

ただしこれは「群を抜く」構想ではありません。**これは定着（解約されない）のための構想です。**
そう位置づけて作るべきで、旗にはしません。

### 3-2-6. 規約・法令の判定

全工程が店舗側で完結し、来店客の画面に一切出ないので、Google層1・層2、景表法、見返りのいずれにも触れません。

**⚠ 危ないところを2つ、自分から書きます。**

1. **`window = now` の使い道。** §3-2-2 の条文（Google導線・投稿依頼の文言・件数を置かない）で塞ぎます
2. **通知に時刻とエリアが載ると、シフト表と突き合わせて事実上スタッフが特定できます。**
   ランキングを作らないだけでは足りません。仕様に条文として
   **「個人が一意に定まる粒度での絞り込み機能を作らない」**「原因の紐づけ先は工程（ホール／厨房／会計）と時間帯だけ」
   を書き、`staff_id` の列を**スキーマに置きません**（置けないようにします）。
   これはGoogleの明文禁止の趣旨（一定数のクチコミを募るようスタッフに要求すること）と同じ場所にあり、
   かつ現場の信頼を壊して製品自体が使われなくなるためです

**来店客の本文を外部（Cloudflare／TypeSafe AI）へ送ります。** §5-3 の越境移転の整理が着手条件です。

### 3-2-7. 工数と、いつ出せるか

**7人日。** 内訳：Jev呼び出し2日／通知の文面と「対応した」ボタン1.5日／管理画面の並べ替え2日／目視の精度検証1.5日。

**前提条件が1つあります。** `strategy` §4-2 の #7（届け先を記録する列を足し、低評価アラートの発火条件を付け替える）
を先に済ませること。これはリリースAに含まれています。

### 3-2-8. 誰がいくら払うか

**既存の月9,800円に含めます。値上げしません。**

理由：レビューSaaSの解約理由は「件数が増えたあとに、開く理由がない」です。
これは**毎営業日ひらく理由**になるので、値上げではなく LTV（＝1人の顧客が生涯で払う総額）で返ってきます。
月1,000円の値上げより、解約率が月3%→2%になるほうが効きます。

**将来の値上げの種：** 「対応した」ボタンで**届いてから直るまでの秒数**が貯まります。
これは他社が1件も持っていない指標で、しかもGoogleにも景表法にも無関係なので、
多店舗オーナーが店舗間を**堂々と比較できる唯一の運営指標**になります。
ただし **1年運用してデータが出るまで、値上げの根拠にはしません**（いま語ると嘘になります）。

⚠ この指標を**店頭やLPに出すのは第1版ではやりません**。「当店の平均対応時間4分」を対外表示すると、
測り方・母数・期間を明示しない限り景表法の優良誤認になりうるためです（＝店舗内部の指標に限定）。

## 【本命3】期待の計器 ── 満足度の式に、ずっと足りていなかった左辺

**一文の定義**

> **施術台でうつ伏せになっている20分、シャンプー台の天井を見ている15分に「今日ここに来た理由」を聞き、
> 帰りの評価を「期待との差」として初めて測る計器。飲食ではなく、整骨院・美容室・クリニック・サウナのための構想。**

### 3-3-1. 何が決定的に変わるか（ここが今回いちばん大きい発見です）

37件の構想すべてが、**「体験の結果」だけを測っていました。** ★も、自由記述も、話題タグも、全部が結果の観測値です。

**しかし満足は、結果そのものではなく「結果と期待の差」です。**
同じ15分の待ち時間が、初めて来た人には長く、混むと知って来た人には短い。
同じカットが、髪を切りに来た人には十分で、気分を変えに来た人には不足です。

> **37件のうち、来店客が「何を期待して来たか」を取る構想は0件でした。**
> これは「分析の精度」の問題ではなく、**方程式の変数が1つ足りない**という問題です。
> ★の平均を何年見ても「なぜ★2なのか」が出ないのは、そのためです。

そして、**この左辺を取れる場所が、飲食ではなく非飲食にあります。**

整骨院・美容室・クリニック・フィットネス・サウナには、飲食に無いものが4つあります。

1. **滞在が長く、一人で、手が空いていて、暇。** うつ伏せの20分、カラー剤を置いている30分、待合の15分。
   **世界で最も暇な時間**で、そこに画面があります。飲食の「席にいる間」は連れがいて、料理があって、画面など見ません
2. **結果が数日後に出る**（腰が楽になったか、カラーが馴染んだか）。それなのにGoogleレビューは当日書かれます
3. **来る前が存在する**（予約制）ので、期待がそもそも取りやすい
4. **担当が1対1で決まっている**（だからこそ §3-3-6 の自制が最も厳しく効きます）

市場も飲食より分厚い ── **美容所 277,752施設（前年度比 +3,682、増え続けている）**、一般診療所 104,894施設
（出典: 令和6年度衛生行政報告例／令和5年医療施設調査。`strategy` §3-6）。

**そして重要なこと：この構想は GOOD ORDER（注文SaaS）を必要としません。**
群を抜く審査が1位・2位に推した [33] GOOD MISS と [34] GOOD SENSE は、どちらも素晴らしい構想ですが、
**GOOD ORDER はこのリポジトリに1行も実装がなく、工程表は2027年以降**です（実装審査の判定は 0/10）。
**ORDER を待たずに段2の上端に立てる道は、この構想だけです。**

### 3-3-2. 画面と体験

**来店客側（滞在中）**

うつ伏せの顔の穴の下、シャンプー台の天井、待合の席、ロッカーの内側にQRを置きます。
**不満は聞きません。**（「水が欲しい」に相当するものが非飲食にはほとんど無く、
そもそも不満を検知して何かを提供する設計は、制約3の入口になります）

**軸を1つ間違えても、施術者が読むのは本人の生の文章**です。隣に正しいものが必ず並んでいるので、
施術者が自分の目で判断し直せます。**検査層のように「外すと公開文が壊れる」種類の間違いではありません。**

**ただし、ここには他の2つに無い重さがあります。**
医療・施術の文脈で、**本人が言っていない主訴がAIの要約として届いたら**、害は飲食の誤配とは桁が違います。
**だから型で塞ぎます。** Jev は文章を書けないので、届くのは常に本人の文そのものです。
**書けないAIであることが、ここでは安全装置そのものになっています。**

**退避：** Jev が落ちたら、軸を出さずに**本人の文章だけ**を施術者に届けます。それでも価値の大半は残ります。

### 3-3-5. なぜ競合が真似できないか

**機能は真似できます。真似できないのは順序です。**

競合5社は全員「帰り際のクチコミ獲得」に製品を最適化しており、**来店前・滞在中に画面を持っていません。**
そこに入るには、製品の入口を作り直す必要があります。

そして本命の堀は**期待と結果の対の履歴**で、これは時間でしか貯まりません。
貯まると「この店は、どの期待に応えられていないか」という、**クチコミには一度も現れない指標**が出ます。

### 3-3-6. 規約・法令の判定

**⚠ この構想の危険は4つあり、全部が新しい種類です。ここだけは慎重に読んでください。**

1. **医療広告規制（未確認。着手前に必ず潰すこと）。**
   医療法6条の5と医療広告ガイドラインは、**患者の体験談を広告に用いることを原則禁止**しています。
   柔道整復・あん摩マッサージ・はり・きゅうはさらに厳しく、広告できる事項が法律で限定列挙です。
   **この論点は、37件の構想にも3つの審査にも1度も出てきませんでした。**
   この構想は**店内に閉じている**（集めた声を公開側に出さない）ので原則セーフと読めますが、
   **一次情報の確認が着手条件**です。天真さんの判断項目です。
   条文として「**クリニック・柔整・あはきでは、集めた声を公開側に出す機能を作らない**」を仕様に固定します
2. **Google層1（gating）。** 滞在中に書いたかどうかで、帰りの届け先2枚を**1ミリも変えません。**
   これは口約束ではなく、**機械検査で担保します**（`npm run check` に1段足し、滞在中モジュールの値が
   届け先画面のレンダリングに到達しないことを検査する）
3. **スタッフ別ランキング。** 担当が1対1で決まる業態なので、期待と結果の対を担当者に紐づけた瞬間に、
   **実質的なスタッフ別評価が完成します。** `staff_id` を**スキーマに置きません**。
   これは規約ではなく**思想による制限**だと仕様に明記します
4. **匿名性。** 滞在中の回答と帰りの回答を結ぶキーが要ります。
   **その日その施術台限りの番号までにとどめ、会員ID・端末ID・予約IDには触れません。**
   予約システムと繋ぎたくなりますが、繋いだ瞬間に、殺した構想[37]（離反予測）と同じ場所に落ちます

**層2（内容への影響）：** 滞在中の画面はレビュー導線と**画面的にも時間的にも完全に分離**します。
滞在中の画面から★にもGoogle導線にも一歩も進めません。

## 4-1. 法律で殺したもの（形を変えても採らない）

## 最後に、一言だけ

天真さんが「泥臭い戦いになる気がする」と言ったのは、正確な直感でした。
**泥臭い戦いの正体は、勝敗を他社と同じ指標（件数と星）で測っていることです。**

件数と星の土俵には5社いて、価格も9,800円で揃っていて、AIが書くことも全社やっています。
そこで勝とうとする限り、**どれだけ良いものを作っても比べられる相手が同じ**です。

**だから、測るものを変えます。**

「何件増えたか」ではなく「**どう読まれているか**」。
「何点だったか」ではなく「**まだ間に合うか**」。
「結果がどうだったか」ではなく「**何を期待して来た人の、何に応えられなかったか**」。

この3つは、他社が1つも持っていません。そして**3つとも、文字を書けないAIにしか測れません。**

> **AIは書きません。測ります。**
