## 1. 決定事項（2026-08-28、天真）

1. **宛先を選ぶ画面は、全員に完全同一の1枚を出す。** ★4-5と★1-3でカードの並び順を
   入れ替える案（Figma確定済みだった）は**廃止**する。順序効果という規約上の緊張関係も同時に消える
2. **★の総合評価は最初に聞く。** 途中離脱でも最低限の評価が残り、既存の集計とも互換が保てる
3. **v1の範囲は「最大8判断・全問スキップ可・音声入力なし」。** 増やすのは完了率の実測後

## 2. 設計の原則

### 2-1. 1画面1判断

「1画面1質問」ではなく **1画面1判断**。判断が1つなら、複数の選択肢に触れてもよい（複数選択）。

- **単一選択はタップした瞬間に次へ進む**（「次へ」を押させない）。これが軽さの正体
- **複数選択のときだけ確定ボタンを出す**（何個選んだかを本人が決めるため）
- **全問スキップできる。** スキップは離脱ではなく正常な回答
- **常に戻れる。** 誤タップは必ず起きる
- 進捗は**問数ではなく所要時間で伝える**（「あと約20秒」）。「8問」と見せると重くなる

### 2-2. 選択肢は「感想の断片」にする

v1の失敗は、**「料理・味」という1単語から200字を作らせていた**こと。
材料が足りないまま作文させると、本人が言っていないことで埋まる（＝FROMAのステマ指摘の直接原因）。

| v1（項目ラベル） | v2（感想の断片） |
|---|---|
| 料理・味 | パンがふわふわだった／盛り付けがきれいだった |
| 接客・スタッフ | 店員さんが感じよかった／説明が分かりやすかった |
| 雰囲気・内装 | 席がゆったりしていた／落ち着いて過ごせた |

右は**そのまま文の部品**になる。5つ選べば5つの事実が集まり、AIの仕事は「作文」から
「接続と語尾の調整」に変わる。**AIが盛る余地が構造的に消える。**

### 2-3. 分岐してよいもの / いけないもの

> **分岐してよいのは、体験を深掘りする質問。分岐してはいけないのは、宛先。**

- 「料理が印象に残った」を選んだ人にだけ料理の質問を出す ＝ **してよい**
- ★の数で宛先の出し方を変える ＝ **してはいけない**（規約の3要件に触れる）
- **どの経路を通っても、最後の宛先画面は完全に同一**

### 2-4. 良かった点と気になった点を、両方聞く

★5の人にも「少し気になったこと」を聞き、★2の人にも「良かったこと」を聞く。
現実の体験は満足／不満の二択ではない。混ざった感想を書けることが、口コミの信頼性を上げる。

### 2-5. 出力は入力に比例させる

1つしか選ばれていなければ、原則1文しか作らない。足りなければ**文章を膨らませず、質問を1つ足す**。

## 3. 操作の流れ（全体）

```
[1] 星（1判断・単一）        ← 全員。ここは v1 と同じ位置
[2] 来店文脈（1判断・単一）   ← 初めて / 何度か / いつも
[3] 印象に残った領域（1判断・複数） ← ここで以降の分岐が決まる
[4] 深掘りA（1判断・複数）    ← [3]で選んだ1つ目に対応
[5] 深掘りB（1判断・複数）    ← [3]で選んだ2つ目に対応（無ければ飛ばす）
[6] もう片方の面（1判断・複数） ← ★4-5なら「気になったこと」、★1-3なら「良かったこと」
[7] ひとこと（1判断・任意）    ← スキップ可
[8] AI下書きの確認（1判断）    ← 編集できる
    ↓
[9] 宛先を選ぶ（全員同一の1枚）
    ↓
[10] Google に投稿 / お店に届けた（サンクス）
```

**実際に通るのは6〜8画面**（[5]は選択次第で飛ぶ、[7]はスキップ可）。
**[6]の中身だけが★で入れ替わる**が、これは体験の深掘りであって宛先の出し分けではない（2-3）。

### 3-1. なぜ [6] を入れるか

★5の人に「気になったこと」を聞くのは、店にとって最も価値のある情報が取れるからであり、
★2の人に「良かったこと」を聞くのは、その人の感想が「批判だけ」にならないようにするため。
**どちらも「特になし」を選べる。**

## 4. 質問セットの実例（YORKYS BRUNCH／夙川）

**共通の骨組み（全業態）＋ 店固有の選択肢**、という構成にする。
店固有部分は Phase 2 で AI が提案し、店主が確認・編集して確定する（当面は業態プリセット＋手編集）。

```
[1] 今日の体験はいかがでしたか？
    ★5 とても満足 / ★4 満足 / ★3 ふつう / ★2 やや不満 / ★1 不満        ← 単一・自動送り

[2] 今日で何回目のご来店ですか？
    初めて / 何度か来ている / いつも来ている                              ← 単一・自動送り

[3] 特に印象に残ったのは？（いくつでも）
    料理 / ドリンク / 接客 / お店の雰囲気 / 待ち時間 / 値段              ← 複数・確定ボタン

[4] （料理を選んだ人）今日召し上がったものは？
    パンケーキ / フレンチトースト / エッグベネディクト / パスタ / その他   ← 複数・店固有

[5] （パンケーキを選んだ人）どうでしたか？
    ふわふわだった / 口の中で溶けた / 見た目で歓声が出た /
    思ったより軽かった / 量がちょうどよかった / 待った甲斐があった        ← 複数・店固有

[6-a] ★4-5 の人： 少し気になったことはありますか？
      特になし / 待ち時間 / 席の間隔 / 値段 / 店内の音                    ← 複数・「特になし」が先頭

[6-b] ★1-3 の人： 良かったところもあれば教えてください
      特になし / 料理の味 / 接客 / 雰囲気 / 立地                          ← 複数

[7] ひとことあれば（任意）
    自由記述。スキップできる
```

**[5]・[6-a]・[6-b] には、選択肢の下に任意のテキストフィールドを置く**（2026-08-28 天真）。
選択肢に無いことを書きたい人の受け皿。空のまま進めてよい。
**ここに書かれた言葉は本人の言葉そのものなので、AI下書きで最優先の材料**にする。

**選択肢の語彙が店の実体そのものになる**（「ぷるぷる」「マスカルポーネ」等）。
検索語を書かせるのではなく、体験を具体的に聞いた結果として店の特徴が声に残る（方針§7）。

## 5. ルート実例

### 5-1. 満足したお客様（★5）

```
★5 → 「初めて」 → 「料理・接客」 → 「パンケーキ」
  → 「ふわふわだった・見た目で歓声が出た」
  → 接客「説明が分かりやすかった」
  → 気になったこと「特になし」
  → ひとこと（スキップ）
  → AI下書き（4つの断片から3文）→ 確認
  → 宛先を選ぶ（同一の1枚）→ Google を選ぶ
```

生成される下書きの想定（**選んだ内容だけ**で構成）:

> 初めて伺いました。パンケーキがふわふわで、見た目にも歓声が出ました。
> 店員さんの説明も分かりやすかったです。

**「また来たい」は本人が選んでいないので入れない。** これが v1 との決定的な違い。

### 5-2. 気になったことがあったお客様（★2）

```
★2 → 「何度か来ている」 → 「待ち時間」
  → 深掘り「料理が出てくるまで長かった」「30分以上待った」
  → 良かったところ「料理の味」
  → ひとこと「悪くはないけど、待ち時間の案内が欲しかった」（記入）
  → AI下書き（良い面と気になった面の両方を含む）→ 確認
  → 宛先を選ぶ（**満足客とまったく同じ画面**）→ お店に届けるを選ぶ
```

想定される下書き:

> 何度か利用しています。料理の味は良かったのですが、今回は提供までに30分以上かかりました。
> 待ち時間の案内があると助かります。

**この人も Google を選べる。** そこを塞がないことが製品の芯（`review-flow-rationale.md` §3）。

## 6. AI生成のルール（v2）

### 6-1. 現行実装の何が問題か（監査結果）

`lib/rating-flow/generate-draft.ts` の SYSTEM_PROMPT は、
**「200字程度」と長さを固定**し、**「★5なら『また来たい』を含める」ことを強制**している。
`lib/rating-flow/fallback-draft.ts` も★5で「また利用したいと思います。」を無条件に足す。
**FROMAのステマ様文面の直接原因はここ。**

### 6-2. v2 のルール

1. **入力に比例させる。** 断片1つなら1文。字数の下限を設けない
2. **本人が選んでいない感情・再訪意向・推薦意向を足さない**（「また来たい」は選択肢として
   本人に選ばせたときだけ使う）
3. **回答に無い事実を作らない**（料理名・金額・時間）
4. **AI特有の定型表現を避ける**（「心温まる」「素晴らしいひととき」「ぜひまた訪れたい」）
5. **自由記述があれば、その語彙と文体を残す**（清書しすぎない）
6. **同一店舗の直近の下書きと類似度を検査**し、閾値超えなら書き直す
   （`ai_draft_logs.output_text` に全文が残っているので実装可能）
7. **構造化して返させる。** 各文がどの回答（AnswerSignal）から来たかを保持し、
   **裏づけのない文が1つでもあれば投稿候補として表示しない**

### 6-3. 画面に出す言葉

> あなたが選んだ内容だけで下書きを作りました。

出典の対応データは v1 から保持する（構造化出力の副産物なので追加コストはほぼ無い）。
**タップで出典を表示するUIは、プロトタイプ検証の後に判断する。**

⚠ **プロンプトの文面そのものは CLAUDE.md 3章の「止まって確認する」項目。**
実装前に文面を提示して承認を得る。

## 7. 途中離脱・スキップ・戻る

- **スキップは正常な回答**として記録する（未回答と区別する）
- 戻ると前の回答は保持される
- 途中離脱しても、**[1]の★だけは送信済みにする**（決定事項2の理由）
- 通信中も回答を失わない

## 8. v1 の範囲（何を作り、何を作らないか）

| 含む | 含まない（後段） |
|---|---|
| 1画面1判断・自動送り・スキップ・戻る | 音声入力の**機能**（アイコンは置く。下記 8-1） |
| 星→文脈→領域→深掘り→もう片方→ひとこと | 出典タップ表示のUI（データは持つ） |
| 入力比例のAI生成・実体験ガード・類似度検査 | 匿名の受付確認機能（方針§14） |
| 全員同一の宛先画面（案I） | AIによる質問の自動生成（Phase 2） |
| 店固有の選択肢（手で編集） | GOOD ORDER連携（Phase 3・別途技術検証） |

### 8-1. 音声入力（2026-08-28 天真）

**自由記述の欄に、録音・停止のアイコンを最初から置いておく。** v1では押しても動かない
（または「準備中」）でよいが、**場所を先に確保する**。後から足すと配置が崩れるため。

将来の構想：ふつうの音声入力にとどめず、**Typeless のように AI が書き起こしを添削して
正しい日本語に整える**。話し言葉のまま残すか、整えるかは選べるとよい。
**コストと相談**（音声認識＋添削で1回あたりの単価が上がる）。

## 10. 残論：選択肢そのものが文章を似せてしまう問題（2026-08-28 天真の指摘）

**選択肢を用意する以上、多くの人が同じ断片を選ぶ。** ここに性質の違う2種類が混ざっている。

| 種類 | 例 | 重複したときの見え方 |
|---|---|---|
| **事実型** | ふわふわだった／口の中で溶けた／量がちょうどよかった | **問題ない。** 多くの人が実際にそう感じる事実なので、重複は自然 |
| **表現型** | 見た目で歓声が出た／幸せな気分になった | **不自然。** 個性的な言い回しのはずなのに全員の口コミに同じ文が並ぶ |

天真の案：**同義の選択肢を複数用意して、表示のたびにランダムに出し分ける。**

**一旦保留**（ハードルが高いため）。ただし v2 の中心的な狙いが「AIっぽさ・量産感の解消」で
ある以上、**選択肢の設計そのものが量産感を生む**というこの指摘は本質的なので、忘れないこと。

検討の入口（着手時に考える）:
- 選択肢は**事実型に寄せ**、表現型は自由記述・音声入力から拾う（AIが作らず、本人の言葉を使う）
- 同義の言い回しを3つほど持ち、回答者ごとにランダムで見せる（天真案）
- 生成時に、直近の下書きと同じ表現が続いたら別の言い方に振り替える（類似度検査の応用）

## 11. 2026-08-28 夜の再設計（チャッピー資料＋天真の方針。3章の流れを置き換える）

**本質の言語化（天真）：AI作文を主役にせず、本人の感想を発見・具体化するためにAIを使う。**
作文も必要だが、価値の中心ではない。

1. **章は「4ページ」ではなく、縦長フォーム内の意味の章**：
   今日のこと → 料理・サービス → 印象に残ったこと → 伝えたいこと。
   上部に現在の章名＋**「あと2章・約40秒」**（「2/4」だけより負担が正確に伝わる）。
   終えた章は要約になって上に残り、「直す」で戻れる（自動前進で答えを直せなくしない）
2. **商品と感想は item 単位で紐づける**：複数選んだら「特に印象に残った1品」を先に聞く。
   「食べていない」はカテゴリと排他。選択肢は実メニュー（YBmenu.pdf、未確定版）から
3. **AI追質問は情報が足りないときだけ、最大2問**。引き金は
   （a）品を選んだのに具体的な感想が無い／「その他」
   （b）評価が高いのに「待ち時間」が気になった点に選ばれている（どの場面か不明）
   （c）評価が低いのに何が悪かったか選ばれていない。
   **目的は本人の体験の特定。MEOワードを言わせることではない**（越えるとステマ印象に戻る）
4. **器は4状態**：empty（1行）→ writing（4行）→ resting（2行に縮んで質問へ場所を返す）→
   expanded（タップで全文）。**新しく言葉になった句だけ**を淡い黄でハイライト
   （黄のトークンは未整備。warning-wash を仮借用中。本採用時に Figma へ足す）
5. **選択UIは意味で変える**：★＝カード、来店回数＝3分割、複数選択＝チップ。
   全幅カードの縦積みに統一しない
6. **下書き画面の操作は階層を分ける**：文体＝排他の切替（segmented）／絵文字＝トグル／
   別の言い方＝アクション。編集欄は内容に合わせて伸縮

## 12. 2026-08-28 深夜の修正仕様（実機検証P0〜P2。天真承認済み）

実機検証で**回答に無い内容の生成**（「厚みがあった」→「食べ応えがあった」等）と
**AIエラー文の露出**が見つかり、canonical fact model へ全面移行した。

1. **canonical fact model**（`lib/demo/fact-model.ts`）：全回答を id 付きの Signal として持ち、
   生成文（Sentence）は必ず sourceSignalIds を持つ。**検証層**（既知id・禁止語・メタ発言・
   事実の取りこぼし）を通らない生成は**全体を破棄し、直前の正常な文章を維持**する
2. **★は集計専用。** プロンプトへ一切渡さない（パラメータ自体を廃止＝構造的に混入不可能）
3. **絵文字は決定論**（`applyEmoji`）。AIを呼ばない。絵文字なしの本文を常に別に保持し、
   OFFはそれを表示する（構造的に可逆）。句点の代わりに文末へ置く
4. **評価による質問の出し分けを廃止。** 章3は全員共通の2問
   （良かったところ→気になったところ。どちらも「特になし」可）。
   AI追質問の引き金も★非依存（品の感想が無い/「その他」・待ち時間の場面が不明）のみ、最大2問
5. **Living Draft**：選択の瞬間にルールベースの仮文で即時反映（追加はタイピング、解除は演出なし）。
   章の終わりに Haiku が非同期で整文（検証を通ったときだけ差し替え）。最終は Sonnet。
   **「直す」で戻っても文章は消えない**（回答を変えた章の文だけが組み直る）
6. **手動編集後は生成操作をロック**し「AIの文に戻す」で解除（2026-08-28 承認）
7. 器の高さ：empty=1行 / writing=3行 / resting=2行 / expanded=全文
8. 品の感想の選択肢：**味・食感・温度・量・見た目・香りの軸で肯定・中立・否定をバランス**。
   品を選んだ時点で先読み。店舗の事前承認は本実装時の設計対象
9. 出口画面：全文表示（3行で切らない）。「代表が直接読みます」→**「お店の担当者が確認します」**
10. 進捗は「あと◯章」（秒数は実測と合わないため撤去）
11. **必須テスト**：`node scripts/demo-fixtures.mjs`（devサーバー起動中に実行）。
    高評価・低評価・混在の3ルート＋絵文字の可逆性。実装と同じ `validateSentences` を使う

## 13. 2026-08-28 深夜（2）— 連続インタビュー化（天真承認済み）

## 14. 複数選択の進行（2026-08-28、実機フィードバック）

**「いくつでも選べます」と言いながら、1つ選んだ時点で次の質問が視界に入ると、
1つ選べば終わりだと受け取られる。** 複数選択では、本人が「選び終えた」と決められることが要る。

| 種類 | 進み方 |
|---|---|
| **single** | 選択後 520ms で次の未回答へスムーズにスクロール。進捗もここで進む |
| **multiple** | **1つ目でも2つ目でも自動スクロールしない。** 最初の選択が入ったら選択肢の下に
「ほかにも選べます。あとから変更できます」＋**右寄せの小さなアウトライン「選び終わった ↓」**を出す。
押して初めて次へ進み、進捗も進む |

- **「次へ」という文言は使わない**（画面遷移・フォーム送信に見せない）。塗りボタンにもしない
- **子質問（カテゴリ→品）は同じブロックの中**に開く。**品を1つ以上選ぶまで「選び終わった ↓」を出さない**。
  カテゴリを足せば、その品も同じブロックに増える
- 終えた質問は**コンパクトな要約**になり「変更」で再展開（選択状態は保持）。小さな「畳む」は廃止
- **進捗は「選び終わった」を押した時にだけ進む。** 次の質問がDOMに現れただけでは進めない
- 「この感想を仕上げる」は**感想が成立するまで出さない**（常時disabledは「まだ終われない」圧になる）

実測：複数選択の1つ目で `scrollY 0 → 0`（画面が動かない）。「選び終わった ↓」で次の質問へ遷移。

## 15. 「選択 → 言葉になる」演出（2026-08-28）

タップした事実が感想文へ変換されることを、**説明なしで体験させる**ための演出。
派手なゲーム演出ではなく、静かで気持ちのよい「言葉の変換」として作る。

- タップした瞬間、**元の選択肢は即座に選択済み**になる（演出は操作をブロックしない）
- 選択肢のコピー（ゴーストチップ）が生まれ、**420ms**で器の中へ移動する。
  少し上に浮いてから下へ入る（`cubic-bezier(0.32, 0, 0.2, 1)`、中間で -14px）
- 到着した語句は器の中で**一瞬だけ淡いイエロー**になり、**700msで透明へ**フェードする
- **文章全体には敷かない。** 追加・更新された語句だけを光らせる
- **器が画面外なら飛ばさない**（見えないところへ派手に飛ばさない）。ハイライトだけ行う
- 連続タップは**最新3件まで**に間引く
- 解除では飛ばさない。「特になし」でも飛ばさない
- `prefers-reduced-motion` では移動を省略し、ハイライトだけにする

**AI待ちにしない。** タップ直後の反映はルールベースの material chip で即時に行い、
AI整文は idle 700ms で非同期に走る。検証を通ったときだけ文章単位で差し替え、
差し替えた部分だけ下線が走る。**生成中・失敗の文言は画面に出さない。**

## 16. 実機フィードバック6点の反映（2026-08-28）

1. **画面遷移の遅延を解消。** single の待ちを 520ms → **260ms**、スクロールの遅延を 120ms → 40ms
2. **選んだ履歴はすべて器に入る。** 「パンケーキ」等のカテゴリも Signal 化した。
   **`includeInDraft` は「文章の材料にするか」だけのフラグで、表示の可否ではない**
   （飛ぶアニメーションは出るのに器に入らないのは矛盾、という指摘）。
   品まで選ばれたカテゴリは、文章の材料からだけ外す（品名と重複するため）
3. **自動整文の条件を調整。** debounce 700ms → **600ms**。閾値は
   「材料2つ以上 **かつ** 『どうだったか』に当たる材料（品名・カテゴリ以外）が1つ以上」。
   品名だけでは文章にならないため。実測で「次へ」を押さずに refine が走ることを確認
4. **質問セクションの枠を戻した**（展開中はミントの薄枠、要約はグレーの枠）
5. **器をすりガラスに。** `backdrop-filter: blur(20px) saturate(180%)`、
   背景は `color-mix` でトークンから作る（生の色コードを書かない）。上端に薄い光の線
6. **吸い込みを改善。** 420ms → **640ms**。いちど浮いてから器へ向かい、**最後に器の中へ吸い込まれる**
   （scale 0.6 まで縮む）。着地点は器の左上ではなく**chip が並ぶ場所**の座標を実測して狙う
