## A. 画面フローと分岐の定義

### A-1. 画面遷移

```
[QRコード読み取り]
        ↓
   01 評価トップ (1:324)
   星1〜5を選択 → 「回答する」
        │
        ├─ ★4 または ★5 ─────────────┐
        │                              ↓
        │                    02 良かった点 (1:360)
        │                    タグ複数選択＋自由記述(任意)
        │                    → 「回答する」
        │                    （評価・タグ・自由記述を送信、同時にAI下書き生成を開始）
        │                              ↓
        │                    03 下書き結果・コピー (1:382)
        │                    ①コピー → ②Googleマップを開く → ③貼り付けて投稿
        │                    ★4以上フローはここで完結（05サンクスは削除済み・存在しない）
        │
        └─ ★1〜★3 ────────────────────┐
                                        ↓
                          04 改善アンケート (1:306)
                          チェック複数選択＋自由記述(任意)
                          → 「送信する」
                                        ↓
                          06 サンクス (1:415)
                          完了表示＋任意の Google 投稿導線
```

### A-2. 分岐の入口

01画面は共通（★の値に関わらず同一画面）。「回答する」タップ時点で星の値により02または04へ分岐する。
星の境界（★4以上＝良かった点フロー／★1〜3＝改善アンケートフロー）は固定値として決定済み（2026-08-05 天真確認）。
店舗ごとに境界値を変える設定は設けない。

### A-3. 戻る操作

5画面いずれにも「戻る」ボタンは存在しない（Figma実測）。来店客がその場でQRを読んで一発で答える想定のフローであり、
評価をやり直したい場合はブラウザの戻る操作に委ねる想定。ブラウザバックへの対応（前の入力を保持するか、まっさらに戻すか）は
実装時の判断でよい（公開挙動が変わらない範囲のため、CLAUDE.md 3節の「自分で判断してよい」に該当）。ただし、
**03画面（AI下書き提示後）からブラウザバックで02画面に戻り、再度「回答する」を押すと二重送信・二重下書き生成が起きる**。
これは実装で防ぐ（送信済みフラグ or 冪等キーでガードする）べき技術的な論点であり、天真の確認は不要。

### A-4. 途中離脱の扱い

**画面02または04で「回答する」/「送信する」を押すまでは、何も保存しない。** 星・タグ・自由記述はすべてクライアント側の
ローカル状態にとどめ、途中でタブを閉じても店舗側には何も届かない。DB書き込みが発生するのは以下の2箇所のみ：

1. 02画面「回答する」→ 評価・タグ・自由記述の保存 ＋ AI下書き生成のトリガー（★4以上）
2. 04画面「送信する」→ 評価・チェック・自由記述の保存（★3以下）

この設計にする理由：01画面での星選択だけでは「回答」として完結しておらず、中途半端なレコードを残さないため。

### A-5. URL設計（提案）

- **入口URL**：店舗ごとに1つ。`https://app.goodloop.jp/r/[storeSlug]` を想定（2026-08-05 天真決定）。
  `goodloop.jp` は公式サイト（オフィシャルサイト）用に温存し、アプリ本体は `app.goodloop.jp` サブドメインで運用する。
  `storeSlug` の命名規則はE-10参照（天真から実装時判断に委任）
- **画面間の遷移**：01→02→03（★4以上）、01→04→06（★3以下）のいずれも、**別URLに遷移させずクライアント側の状態遷移で行う**
  提案。理由：
  - CLAUDE.md 4章の「同期的な `await action()` → `router.refresh()` パターンは使わない」という規約と方向性が一致する
    （画面ごとに全体再フェッチすると、モバイル回線で1画面ごとに待たされる体感になる）
  - この5画面はいずれも「次のステップに進むための入力フォーム」であり、ブラウザ履歴に個別URLとして残す価値が薄い
    （むしろ03画面（下書き結果）だけ別タブで開き直される、といった事故を避けられる）
  - 状態（評価・タグ・自由記述・生成済み下書き）をURL間で受け渡す設計を作らずに済む
- **サーバー処理はAPI Routeで行う**（提案。実際のパス名は実装時に決めてよい範囲）：
  - 評価・タグ・自由記述の送信（02画面の送信、04画面の送信）
  - AI下書き生成・再生成（B節参照）

これは技術的なアーキテクチャの提案であり、公開挙動（見た目・文言）を変えるものではないため、実装時に細部を調整してよい。

## B. AIの下書き生成の方式（3案）

入力は「星の数＋選んだタグ＋自由記述（あれば）」のみ。ここから自然な日本語のクチコミ下書きを作る。

料金・速度は `/claude-api` スキルの現行モデル表（2026-06-24キャッシュ、確認済み）に基づく概算。
入力トークン数は「システムプロンプト＋星＋タグ＋自由記述」で400〜600トークン、
出力は200字程度の日本語クチコミで150〜300トークン程度と仮定した試算。

### 案1（推奨）：リアルタイムAPI呼び出し（Claude Haiku 4.5）

02画面の「回答する」送信を受けて、サーバー側（Next.js API Route）から都度 Claude API を呼び出し、
その場で下書きを生成する。

| 項目 | 内容 |
|---|---|
| モデル | `claude-haiku-4-5`（$1.00 / $5.00 per MTok、入力/出力） |
| コスト概算 | 1回あたり **約0.15〜0.3円**（入力500トークン+出力250トークン程度と仮定。再生成を数回しても1客あたり1円未満） |
| 応答速度 | Haiku は低レイテンシ帯のモデル。ネットワーク込みで体感2〜4秒程度を想定 |
| 失敗時の見え方 | タイムアウト（例：5秒）でフォールバック文面（案3のテンプレート合成）に自動で切り替え、お客様を待たせない |
| 実装の重さ | 中。API Route＋Anthropic SDK呼び出し＋プロンプト設計＋フォールバックロジックが必要。新規インフラは不要 |

**長所**：自由記述の内容（例：「パンケーキがふわふわで感動しました」）を下書きに自然に反映できるのはこの案だけ。
**短所**：API呼び出しのぶん、他の2案よりレイテンシとわずかなコストが乗る。

### 案2：事前生成バリエーションプール

管理側で「星評価×タグの組み合わせ」ごとに、あらかじめ複数パターンの下書き文をAI（Haiku等）でバッチ生成しDBに保存しておく。
実行時はAI呼び出しをせず、該当パターンをDBから選択して提示する（自由記述があれば末尾に軽く挿入する程度）。

| 項目 | 内容 |
|---|---|
| モデル | バッチ生成時のみ使用（実行時はAI呼び出しなし） |
| コスト概算 | 実行時は**実質0円/回**。事前生成コストはバッチ処理としてまとめて発生（頻度次第だが無視できる規模） |
| 応答速度 | 数十ms（DB読み取りのみ） |
| 失敗時の見え方 | 実質失敗しない（通常のDB可用性の範囲を除く） |
| 実装の重さ | 大。タグの組み合わせ数の設計、バッチ生成パイプライン、自由記述の扱いが弱い（固有の言及を落とすか雑な差し込みになりがち） |

**短所**：自由記述の具体的な内容を活かせない。「本当にその人の体験を書いた文章」という価値が薄れる。

### 案3：ルールベース・テンプレート合成（AI不使用）

星評価とタグから、あらかじめ用意した文型テンプレートに機械的に当てはめて文章を組み立てる。AI呼び出しは一切行わない。
自由記述があればそのまま末尾に追加する。

| 項目 | 内容 |
|---|---|
| モデル | 不使用 |
| コスト概算 | 0円/回 |
| 応答速度 | 即時 |
| 失敗時の見え方 | 失敗しない（ロジックのみ） |
| 実装の重さ | 小〜中。文型テンプレートの設計とタグ×星のパターン網羅が必要 |

**短所**：03画面の「AIが下書きを作成しました」バッジと実態が食い違う。フォールバック時の文言はE-7で決定済み。

### 推奨と理由

**案1（リアルタイムAI生成）を推奨し、失敗時のフォールバックとして案3のテンプレート合成を流用する。**

理由：自由記述を自然に反映できるのは案1だけであり、これが「クチコミ下書き」としての価値の核。
コストは1回0.2円程度で無視できる水準、Haiku 4.5の低レイテンシで体感速度も許容範囲。
生成失敗時は案3のテンプレートに即座に切り替えることで、「生成に失敗してお客様を待たせる」問題も回避できる。
案2はコストゼロだが自由記述を活かせない点で見劣りする。

### 文体トーン（2026-08-05 天真決定）

カジュアルすぎず丁寧すぎない、一般的な敬語（ですます調）を基本とする。文面ごとの多少のばらつきは
重要視しない（AI生成の性質上、完全な統一は目指さない）。プロンプト設計時のトーン指定として扱う。

## C. Google 誘導の実装詳細

### C-1. 「この文章をコピー」→「Googleクチコミを投稿する」の2ステップ

- **コピー処理**：`navigator.clipboard.writeText()` を想定。iOS Safari はユーザー操作（クリックイベント）に
  同期して呼び出す必要があり、非同期処理を挟むと失敗する場合がある点に注意（コピー処理はボタンのクリックハンドラ内で
  直接呼ぶ）。Android Chrome は制約が緩く、同様の実装で問題なく動作する
- **`writereview` URL を開く挙動**：
  - `https://search.google.com/local/writereview?placeid=<PLACE_ID>` はただのHTTPS URL
  - Android Chrome：Googleマップアプリがインストールされていれば、多くの場合アプリ側にインテントで遷移する。
    未インストールならブラウザで開く
  - iOS Safari：Googleマップアプリの有無・OS設定により、アプリで開く場合とSafari上でGoogleの投稿UIが開く場合がある
- **クチコミ欄への貼り付けは手動操作に依存する**：`writereview` は別オリジンのページであり、コピーした文章をJSで
  自動入力することはできない。Step3「クチコミ欄に貼り付けて投稿」は、お客様自身が長押しペーストする操作が前提

### C-2. `place_id` 未紐付け店舗のフォールバック

店舗管理でGoogleマップと紐付けていない店舗は、`writereview` の直リンクではなく店舗のGoogleマップページ
（共有URLとして管理画面に手動登録したもの、または店舗名・住所での検索結果ページ）を開く。
Step2ボタンの文言は「Googleマップを開く」のまま維持し、投稿フォームに直接飛ばない旨を補足する
一言をボタン下に添える（決定内容はE-8参照）。

## D. データの設計（案。マイグレーションは作らない）

天真の承認が必要な項目として、案のみ提示する。以下は `supabase/` 配下に実装する際の粒度イメージ。
店舗に属するテーブルは `tenant_id` 列＋RLS必須（CLAUDE.md 4章のとおり）。

| テーブル（案） | 主な列（案） | 備考 |
|---|---|---|
| `stores` | `id` `tenant_id` `name` `slug` `loop_theme`（業態） `google_place_id`（nullable） `google_maps_fallback_url`（nullable） | 業態テーマと`place_id`紐付けをここで管理 |
| `survey_responses` | `id` `tenant_id` `store_id` `rating`(1-5) `branch`(good/improve) `tags`(jsonb配列 or 中間テーブル) `free_text` `created_at` | ★4以上・★3以下を1テーブルに**統合**（2026-08-05 決定。E-9参照）。タグの語彙差は`tags_master.category`で吸収し、テーブルは分けない。理由：ダッシュボード集計（KPI・NPS・評価内訳・トレンド）が`store_id`＋`created_at`＋`rating`の組み合わせを横断するため、1テーブルの方が集計クエリが単純になる |
| `ai_draft_logs` | `id` `tenant_id` `response_id`(FK) `model` `prompt_version` `output_text` `latency_ms` `success`(bool) `fallback_used`(bool) `regenerate_count` `created_at` | B案の生成ログ。失敗率・再生成率の可視化に使う想定 |
| `tags_master` | `id` `label` `category`(good/improve) `sort_order` | 全店舗共通のタグ選択肢マスタなら店舗に属さない扱いになり、`-- tenant-check-allow: 全店共通のタグ選択肢マスタ` の対象になる想定 |

**ダッシュボード（07 管理画面セクションで設計済み）が集計に使うことを前提に**、`store_id` ＋ `created_at` ＋ `rating` の
組み合わせで期間・店舗別に集計しやすい形を意識した。KPI・NPS・評価内訳・トレンドはこの3列の組み合わせで大半が出せる想定。

### E-5. 重複回答対策（詳細）

ブラウザの`localStorage`に「この店舗のこのQRには回答済み」というフラグを保存し、01画面の表示時にフラグを見て
再回答をやんわり抑止する（例：回答済みの案内を出し、新規回答フォームを表示しない）。

- 完全な重複防止ではない（別ブラウザ・シークレットモード・`localStorage`削除では回避できる）。
  来店客の識別にログインや個人情報を使わない設計とのトレードオフとして意図的に許容する
- サーバー側での重複検知・遮断は行わない（実装コストに見合わないと判断）。DBには毎回そのまま保存する
- フラグの保存キー名・保持期間（無期限か一定期間で失効させるか）は実装時に決めてよい範囲（公開挙動が変わらないため）

### E-7. 03画面バッジ文言（提案）

- **生成成功時**：「AIがあなたの回答から下書きを作成しました」（既存想定どおり）
- **フォールバック時**：AIバッジ自体を非表示にし、代わりに控えめなキャプションで
  「あなたの回答をもとに下書きを作成しました」と表示する（「AI」という語を使わない＝生成主体を偽らない）

### E-8. `place_id`未紐付け店舗のフォールバック文言（提案）

Step2ボタンの文言は「Googleマップを開く」のまま維持し、ボタン直下に小さな注記を添える。

> 投稿フォームは開けないため、Googleマップの中から「クチコミを書く」を選んで投稿してください

### E-10. スラッグ命名規則（提案）

店舗作成時に店舗名からkebab-caseで自動生成し（例：「らーめん花月」→ `ramen-kagetsu`）、重複する場合は連番
サフィックス（`-2` `-3` ...）を付ける。管理画面で店舗側が任意のスラッグに手動変更できるようにする
（読みにくい自動生成スラッグをそのまま固定にしない）。
