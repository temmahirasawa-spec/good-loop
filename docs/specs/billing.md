## 2. 契約の形

**契約の単位は「契約先（テナント）」です。** 店舗ごとではありません。

1つの契約先が、Stripe の1つのサブスクリプション（継続課金）を持ちます。
そのサブスクリプションは、明細を**2行**持ちます。

| 明細 | 数量 | 金額（仮） |
|---|---|---|
| GOOD REVIEW スタンダード | 常に 1 | 月額 9,800円 |
| GOOD REVIEW 追加店舗 | 店舗枠 − 1 | 1店舗につき 月額 3,000円 |

**例：** 3店舗ぶんの枠を契約している場合 → スタンダード×1 ＋ 追加店舗×2 ＝ 月額 15,800円。

**契約は「スタンダード × 1」だけで始めます。** 追加店舗の明細は、店舗枠を増やすときに作ります
（`/api/admin/billing/quota`）。数量0の明細を先に置いておく形は取りません。
Stripe 側で数量0の明細を作ろうとすると弾かれることがあり、契約の入口が壊れるリスクを避けるためです。

枠を1つ増やすときの動きは次のとおりです。

| そのときの状態 | やること |
|---|---|
| 追加店舗の明細がまだ無い | 明細を作る（数量1） |
| すでにある | 数量を +1 する |

どちらも**今月の残り日数ぶんの差額を即時に請求**します（Stripe の `always_invoice`）。
翌月からは増えた数量で満額が請求されます。

## 3. 店舗枠の正はどちらか

**Stripe が正です。** 「決済されたぶんだけ枠がある」という向きにします。

- 店舗枠の実体は今までどおり `tenants.store_quota`（`supabase/0009`）
- ただし Stripe に繋がっている契約先では、**この値は Stripe からの通知で書き換わる**。
  画面や API から直接増やすことはしない
- **Stripe に繋がっていない契約先**（`billing_status = 'none'`。洋輔さんの検証用アカウントなど）は
  今までどおり、運営が Supabase 上で `store_quota` を手で増やす

この二重運用は意図したものです。**カードを登録していない相手にも製品を渡せる**必要があるためです
（検証・デモ・無償提供）。

### ⚠ 枠は、いま使っている店舗数を下回らせない（2026-08-24 追加）

「Stripe が正」を素直に実装すると、**運営が手で枠を増やしていた契約先が、
あとからカードを登録した瞬間に枠を失います。**

> 例：夙川店のテナントは運営が手で `store_quota = 3` にしている。
> ここでカードを登録して「基本プラン（1店舗込み）」の契約が作られると、
> Stripe からの通知で枠が **3 → 1** に書き換わる。
> 既存の3店舗は消えないが枠オーバーになり、以後1店舗も追加できなくなる。

これは実運用で必ず起きる事故なので、二重に防いでいます。

| # | 場所 | やること |
|---|---|---|
| 1 | `/api/admin/billing/checkout` | **いまの枠と同じ数で契約を作る。** 3店舗使っているなら3店舗ぶん払う |
| 2 | `/api/stripe/webhook` | 枠を書き込むとき、**いま使っている店舗数を下回らせない**（保険） |

2 が働くと「払っていない店舗が使えてしまう」状態になりますが、それは未払いと同じ扱いで、
人が連絡して決めます（4章）。**画面が壊れて店舗を追加できなくなるほうが害が大きい**という判断です。

## 4. データベースの持ち方

`supabase/0013_stripe_billing.sql`。**列の追加のみで、既存の列・データは書き換えません。**

| 列（`tenants`） | 中身 |
|---|---|
| `stripe_customer_id` | Stripe 側の顧客ID（`cus_...`）。一意 |
| `stripe_subscription_id` | Stripe 側の契約ID（`sub_...`） |
| `billing_status` | `none` / `active` / `past_due` / `canceled` の4つ |
| `billing_current_period_end` | 今の請求期間の終わり。画面の「次回のお支払い」に出す |

**利用者からは書き換えられません。** `supabase/0009` の
`revoke insert, update, delete on tenants from authenticated` がそのまま効くため、
新しい列も読み取り専用です。書き込むのは Stripe からの通知を受ける処理（service_role）だけです。

`billing_status` の意味は次のとおり。

| 値 | 状態 | 画面の振る舞い |
|---|---|---|
| `none` | カード未登録。運営が手で枠を管理している | 「お支払い方法を登録する」を出す |
| `active` | 正常に課金されている | 通常表示 |
| `past_due` | カードが通らなかった | 管理画面に警告を出す。**店舗は止めない** |
| `canceled` | 解約された | 管理画面に警告を出す。**店舗は止めない** |

> **⚠ 支払いが止まっても、来店客の画面（`/r/[slug]`）は止めません。**
> 卓上POPは既に店に置かれていて、二次元コードを読んだお客様には何の落ち度もないためです。
> 未払いへの対応は、画面に警告を出したうえで**人間が連絡して決める**運用にします。
> 自動で止める仕組みを入れるかどうかは、実際に未払いが起きてから判断します。

## 5. 画面と導線

設定 → お支払い（`/admin/settings/billing`。Figma `73:1399` PC / `75:1862` SP）。

| 操作 | どうなるか |
|---|---|
| お支払い方法を登録する（未登録のとき） | Stripe の入力画面へ移動 → 登録が済むと戻ってくる |
| お支払い方法を変更（登録済みのとき） | Stripe のカスタマーポータルへ移動 → 変更して戻ってくる |
| プランを変更 | 同じくカスタマーポータルへ移動 |
| 請求履歴 | **Figma のデザインのまま自前で表示する**（直近3件）。すべて見る・領収書は Stripe の画面へ |
| 店舗枠を追加する | Stripe 側の数量を +1 して即時に差額を請求 → 通知を受けて枠が増える |

### 表示に使う情報は Stripe から都度取りに行く

カードの下4桁・ブランド・請求履歴は、**データベースに保存しません。**
お支払い画面を開いたときに Stripe へ問い合わせて、その場で表示します。

- 保存すると、Stripe 側で変更されたときに**古い情報を出し続ける**（実物と食い違う）
- お支払い画面は頻繁に開く画面ではないので、都度の問い合わせで速度の問題は出ない
- 問い合わせに失敗しても画面は壊さない。その欄だけ「取得できませんでした」にする

### 「契約済みか」を顧客IDで判定しない（2026-08-24 の事故）

**Stripe の顧客は、カードを登録する前に作られます。** 決済画面を作る時点で必要になるためです。

そのため「顧客IDがあるか」で契約済みを判定すると、**登録が途中で失敗した契約先は
顧客IDだけが残り、カードが無いのに「登録済み」と誤判定されます。**
実際に「お支払い方法を登録する」が画面から消え、先へ進めなくなりました。

**判定は `stripe_subscription_id`（契約があるか）で行います。**

あわせて、決済画面を作る前に **Stripe 側にも契約が無いかを問い合わせています。**
DB の値は Stripe からの通知で入るため、通知が届かない・遅れている間は
「契約が無い」ように見え、もう一度押すと契約が二重になって二重に請求されるためです。
見つかった場合は DB に書き戻して、画面の表示も回復させます。

### いま画面に出ている偽の情報を消す

**現状のお支払い画面には、実在しない情報が出ています（2026-08-24 実測）。**

| 表示 | 実態 |
|---|---|
| お支払い方法「Visa •••• 6411」 | 誰のカードでもない固定の文字列 |
| 請求履歴（2026年5〜7月・各9,800円） | 実在しない請求が3件 |

**契約先にアカウントを渡す前に、必ず消します。** カードが未登録なら「未登録」と出し、
登録済みなら Stripe から取得した実際の値を出します。

## 6. サーバー側の処理

| 経路 | 役割 |
|---|---|
| `POST /api/admin/billing/checkout` | カード登録と初回決済の画面（Stripe Checkout）のURLを作って返す |
| `POST /api/admin/billing/portal` | カード変更・請求履歴の画面（カスタマーポータル）のURLを作って返す |
| `POST /api/admin/billing/quota` | 店舗枠を +1 する（Stripe 側の数量を増やし、差額を即時請求する） |
| `POST /api/stripe/webhook` | Stripe からの通知を受けて DB に反映する。**唯一 `store_quota` を書き換える場所** |

### Webhook が受け取る通知と、やること

| 通知 | やること |
|---|---|
| `checkout.session.completed` | `stripe_customer_id` と `stripe_subscription_id` を保存 |
| `customer.subscription.created` / `updated` | 数量から店舗枠を計算して `store_quota` に反映。`billing_status` と次回請求日を更新 |
| `customer.subscription.deleted` | `billing_status = 'canceled'`。**枠は減らさない**（減らすと店舗が消えたように見えるため） |
| `invoice.payment_failed` | `billing_status = 'past_due'` |

**通知は必ず署名を検証します**（`STRIPE_WEBHOOK_SECRET`）。
検証しないと、誰でも「支払いが済んだ」という嘘の通知を送って店舗枠を増やせてしまいます。

**同じ通知が2回届くことがあります**（Stripe の仕様）。どの処理も「同じ通知を2回受けても
結果が変わらない」形（＝上書き）で書きます。数を足し算しません。

## 7. 鍵が入っていないときの振る舞い

`STRIPE_SECRET_KEY` が設定されていない環境では、**課金の導線を出しません。**
店舗枠の追加は、今までどおりの**申し込み**（`store_quota_requests`。`supabase/0011`）のままにします。

こうする理由は2つあります。

1. 鍵が無い状態で押せてしまうと、押した人にはエラーの理由が分からない
2. Stripe を入れる前に契約が始まる可能性がある（洋輔さんの検証がまさにこれ）

**`supabase/0011`（申し込みの表）は残します。** Stripe に完全移行するまでの間、
両方の運用が並走するためです。

## 8. 金額が決まったら直す場所

**2箇所あります。片方だけ直すと、画面の表示と実際の請求額が食い違います。**

| # | 場所 | 何をする |
|---|---|---|
| 1 | Stripe の商品カタログ | 新しい金額の「価格」を登録し、価格ID（`price_...`）を控える |
| 2 | `.env.local` と Vercel | `STRIPE_PRICE_BASE` / `STRIPE_PRICE_ADDITIONAL_STORE` を新しい価格IDに差し替える |
| 3 | `lib/admin/constants.ts` の `BILLING` | 画面に出す金額を同じ数字にする |

> Stripe では、**登録済みの価格の金額は変更できません**（作り直しになります）。
> 既に契約中の相手がいる場合、古い価格のまま請求され続けるため、
> 契約者ごとの価格の移行が別途必要になります。**契約が始まる前に金額を確定させるのが一番安全です。**

## 8-2. Managed Payments は使わない（2026-08-24 天真の決定）

**Managed Payments** は、Stripe が「販売事業者」として表に立ち、消費税の計算・申告・納付を
代行する仕組みです。**使いません。販売事業者は株式会社UTUTU のままにします。**

| 理由 |
|---|
| `/terms`・`/privacy` が「提供者＝株式会社UTUTU」で書かれており、そちらと食い違わせないため |
| 請求書・領収書を UTUTU 名義で出すため |
| 国内の実店舗向けのため、越境販売の税務を代行してもらう恩恵が薄いため |
| 手数料が上がらないため |

**⚠ Stripe アカウント側の既定は「有効」です。** そのため決済セッションを作るときに
明示的に切っています（`managed_payments: { enabled: false }`)。切らないと商品ごとの
税コード登録が必須になり、`this product tax code is ineligible for Managed Payments`
で決済を作れません（2026-08-24、本番で実際に起きました）。

方針を変えて Managed Payments を使う場合は、**利用規約の「提供者」の記載と、
請求書の発行元名義の整合を先に確認すること。**

## 9. やらないこと（今回の範囲外）

| やらないこと | 理由 |
|---|---|
| 銀行振込・口座振替 | カードのみで開始する決定（1章）。断られたら足す |
| プランの変更（上位・下位プラン） | プランが1つしか無い。複数になってから |
| 日割り計算の作り込み | Stripe の既定（差額を即時請求）に任せる |
| 未払いでサービスを止める処理 | 4章の判断。人間が連絡して決める |
| 請求履歴の4件目以降・領収書PDFの自前表示 | Stripe の画面に任せる。直近3件だけ Figma どおりに出す（5章） |
