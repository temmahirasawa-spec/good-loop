## 2. 契約の形

**契約の単位は「契約先（テナント）」です。** 店舗ごとではありません。

1つの契約先が、Stripe の1つのサブスクリプション（継続課金）を持ちます。
そのサブスクリプションは、明細を**2行**持ちます。

| 明細 | 数量 | 金額（税抜） |
|---|---|---|
| GOOD REVIEW スタンダード | 常に 1 | 月額 9,800円 |
| GOOD REVIEW 追加店舗 | 店舗枠 − 1 | 1店舗につき 月額 5,000円 |

**追加店舗の明細は、数量が1以上のときだけ置きます。** 数量0の明細は作りません
（Stripe 側で数量0の明細を作ろうとすると弾かれることがあり、契約の入口が壊れるリスクを避けるため）。

店舗枠を増やしたときの請求は、**体験中かどうかで変えます。**

| いつ | やること |
|---|---|
| **体験中** | 数量を変えるだけ。**差額の請求は出さない**（`proration_behavior: none`）。体験が終わった日に、そのときの数量で初めて請求 |
| 有料期間 | 今月の残り日数ぶんの差額を**即時に請求**（`always_invoice`。従来どおり）。翌月からは増えた数量で満額 |

### 消費税（Q11）

LP は「表示価格はすべて税抜」と書いています。**2026-09-28 にテスト環境の Stripe を読み取りで確かめたところ、消費税は請求に乗っていませんでした。**

| 確かめたこと（テスト環境） | 結果 |
|---|---|
| スタンダードの価格 | 9,800円・**税抜（`tax_behavior: exclusive`）** |
| 追加店舗の価格 | **3,000円**・税抜（⚠ 5,000円の価格に差し替えが要る。§12） |
| 登録されている税率 | **0件** |

「税抜」の価格は、税率か Stripe Tax を付けないと**税を0円で計算します**（エラーも出ない）。コードにも税を足す処理はありません。
本番の Stripe も同じ作りなら、**9,800円だけを請求し、消費税10%（980円）を取れていない**ことになります。

**決定：10%・外税の税率（Tax Rate）を Stripe に1つ登録し、契約に付ける**（`default_tax_rates`）。国内の10%だけなので、これで足ります。
Stripe Tax（自動計算）は使いません（日本での登録が要り、登録が無いと黙って0円の税を計算するため）。

- 税率のIDは `STRIPE_TAX_RATE_ID` として環境変数に置く（テストと本番で別のID）
- 画面とメールの金額は「税抜」を主にし、今日の請求額・毎月の請求額には**税込も添える**（例：月額 9,800円（税抜）／10,780円（税込））
- すでに契約中の相手の扱い（本番に既存の契約があれば、税率を付け直すか）は、本番を確かめてから決める
- インボイス（適格請求書）の登録番号を Stripe の請求書に載せるかも、あわせて確認する（天真の作業。§15）

## 3. 無料体験（2026-09-28）

### 3-1. 流れ

| # | いつ | お店の人がすること | こちら・Stripe がすること |
|---|---|---|---|
| 1 | 申し込み | 店舗名と業態、会社名・お名前・メール・パスワード（いまと同じ） | 契約先を作る。**体験はまだ始めない**（`trial_ends_at` は空のまま） |
| 2 | 確認メール | リンクを押す（いまと同じ） | メールのアドレスが正しいことを確かめる |
| 3 | カードなし | 管理画面を見る。アンケート項目・業態テーマ・通知などを設定する | 二次元コードと店舗枠の追加の手前に「カードを登録して無料体験を始める」を置く（§3-2） |
| 4 | カードの登録の前 | 料金と「無料体験は1回かぎり」を読む | メールとお店で2回目かを判定し、**カードを入れる前に**結果を見せる（§3-4） |
| 5 | カードの登録 | Stripe の画面でカードを入れる | カードの指紋で2回目かを判定 → 体験ありで契約を作る（**0円**）。2回目なら、料金を見せて「有料で始める／やめる」（§3-3・§3-4） |
| 6 | 登録の直後 | 「今日置けば、14日間まるごと試せます」から印刷用のデータをダウンロードする | 印刷して置くところまで案内する（§3-5） |
| 7 | 体験中 | 管理画面のトップで「残り○日」と、読み取られた数・回答の数などを見る | カウントダウンと数字を出す（§3-5） |
| 8 | 7日目（Q8） | — | 「ここまでの結果」のメール（§3-6） |
| 9 | 3日前 | — | 終わる前のお知らせのメール（結果つき）。Stripe の `customer.subscription.trial_will_end` で送る |
| 10 | 15日目 | — | Stripe が自動で請求する。通れば有料期間へ。通らなければ未払い（§3-8） |
| 11 | 体験中に解約したら | Stripe の解約画面で解約し、理由を1つ選ぶ | 体験の最終日まで使える。**料金はかからない**。終わったらお休み（§3-7・§3-8） |

### 3-2. カードが要る操作（Q2）

**「見る・設定する」はカードなし、「お店で使う」はカードあり**で分けます。

| 操作 | カード | 場所（いまのコード） |
|---|---|---|
| 管理画面を見る（トップ・集計・回答一覧） | 不要 | — |
| アンケート項目・業態テーマ・通知・アカウントの設定 | 不要 | 設定の各画面 |
| 店舗の編集（名前・業態・Google マップの紐付け） | 不要（紐付けたときに2回目の判定をする。§3-4） | `StoreEditModal`・`POST /api/admin/settings/stores` |
| 店舗を作る（**申し込みで選んだ数まで**） | **不要**（決定。Q2） | オンボーディング・設定＞店舗管理 |
| **二次元コードの表示・ダウンロード** | **必要** | 設定＞店舗管理（`QrCard`）・オンボーディングの二次元コードの段 |
| **卓上POPを作る・印刷する** | **必要** | 設定＞卓上POP・`/admin/pop/[storeId]` |
| **店舗枠を増やす（2店舗目以降の追加）** | **必要** | 設定＞店舗管理の「＋ 店舗を追加」・`POST /api/admin/billing/quota` |
| **来店客のアンケート（`/r/[storeSlug]`）** | **必要**（Q2。カードの登録まで止める） | `app/r/[storeSlug]/page.tsx`・回答の API |

**店舗を作ることはカードなしでできる**ようにします（決定。Q2）。アンケート項目は店舗ごとなので、
店舗が無いと「アンケート項目の設定を試す」ができないためです。二次元コードが出ないので、店舗を作っただけでは使えません。
選べる形：

1. **申し込みで選んだ店舗数までは作れる**（**決定**。いまのオンボーディングがそのまま使える）
2. 1店舗目だけ作れる。2店舗目からはカードの登録のあと

**来店客のアンケートも、カードの登録まで止めます**（Q2。二次元コードを出さなくても、URL を割り出されて使われうるため）。

- 止めるのは「**申し込みから来た契約先**で、まだ契約が無い」とき（`tenants.card_required = true` かつ契約なし。§5-2 の5）と、お休みのとき（§3-8）
- 来店客に見せる画面は、お休みと同じ「このアンケートは現在お休みしています／ご協力ありがとうございました」（**新しい文言は作らない**。停止の理由も GOOD REVIEW の名前も出さない）
- **回答を受け付ける API も同じ条件で断る**（画面だけ止めても、API を直接呼ばれると回答できてしまうため）。読み取りの記録（`page_views`）も数えない
- お店の人が自分でアンケートを試せるのは、カードを登録してから（＝体験が始まってから）になる
- **営業経由の契約先（`card_required = false`）は止めない。** いま動いているお店のアンケートは、この変更で止まらない

**鍵（`STRIPE_SECRET_KEY`）が入っていない環境**と、**営業経由で作った契約先**（`billing_status = 'none'`、§3-10）では、
このカードの関門を出しません（いままでどおり使える）。

### 3-3. カードの登録と契約の作り方（Q1）

**2回目の判定（カードの指紋）を、体験が始まる前に行う必要があります。** そのため Stripe の標準の形はそのまま使えません。

| | 案A：先にカードだけ登録（**決定**。Q1） | 案B：Stripe の標準の形 |
|---|---|---|
| Stripe の画面 | Checkout の **setup モード**（カードを預かるだけ。請求しない） | Checkout の **subscription モード**に `trial_period_days: 14` |
| 契約を作るのは | カードの指紋を見て判定したあと、**こちらのサーバー** | Stripe（カードを入れた瞬間に体験が始まる） |
| 2回目だったとき | 料金を見せて「有料で始める／やめる」を選んでもらってから請求する | 体験が始まったあとで気づく。体験をその場で終わらせて請求するしかない（**黙って請求することになる**）か、契約を消して案内し直す |
| 作る量 | 多い（判定・契約の作成・確認の画面） | 少ない |

**案A の手順**

1. `POST /api/admin/billing/checkout` — メールとお店で先に判定し（§3-4）、setup モードの Checkout を作る。
   `payment_method_types` は渡さない（§1-1）
2. Stripe の画面でカードを入れる（3Dセキュア＝本人確認もここで済む）
3. `checkout.session.completed`（setup）を受けたら、預かったカードの**指紋**（`payment_method.card.fingerprint`）を取り出し、
   カードを顧客の既定の支払い方法にして、判定する
4. 体験あり → 契約を作る（`trial_period_days: 14`、明細は §2、**請求は0円**）。判定に使った3つ（カード・メール・お店）を記録する（§3-4）
5. 体験なし（2回目）→ **契約は作らない**。戻り先の画面で料金と理由を見せ、「有料で始める」を押したら契約を作って今日の分を請求する。
   カードの会社が追加の本人確認を求めたら、Stripe の請求書の画面へ案内する
6. 戻り先の画面（`success_url`）と Webhook の**どちらが先に来ても**同じ結果になるようにする。
   同じカード登録（SetupIntent）から契約が2つできないよう、契約の作成には冪等キー（＝同じ依頼を2回送っても1回分しか実行されない印）を付ける

**体験の終わりの日は Stripe を正にします。** 契約の `trial_end` を Webhook で受けて `tenants.trial_ends_at` に書きます
（画面のカウントダウンと、実際の請求日が必ずそろう）。

> いまの `/api/admin/billing/checkout` は subscription モードで、**登録した瞬間に1か月分を請求**しています（2026-09-28 に確認）。
> 体験の残りの日数が消え、LP の約束（体験中に解約すれば料金はかからない）とも食い違うので、この改訂で作り直します。

### 3-4. 2回目の無料体験の判定（Q3・Q4）

**3つのどれかが前に無料体験をしていたら、体験なしで始めます**（初日から有料）。

| 見るもの | いつ見るか | 持ち方 |
|---|---|---|
| メールアドレス | カードを入れる**前**（§3-1 の4） | 小文字にそろえてハッシュ（＝元に戻せない変換）にしてから保存 |
| お店（Google マップのお店の ID＝`place_id`） | カードを入れる**前**。体験中に紐付けたときも | ハッシュにして保存 |
| カード（Stripe のカードの指紋） | カードを入れた**直後**（§3-3 の3） | ハッシュにして保存 |

**黙って請求しません。** 外れたときは、何が理由で外れたか（「このお店は以前に無料体験をご利用いただいています」など）と、
今日お支払いいただく金額を見せ、「有料で始める」を押したときだけ請求します。

カードを入れる前の画面には「**無料体験は、1つのお店・1枚のカードにつき1回です**」と書きます（LP と同じ）。
**メールアドレスでも判定することは、LP には書かない**（2026-09-28 天真の決定）。アプリのカードの登録の前の画面にも書かず、
メールで外れた人には、外れたときの確認の画面で理由として伝えます。

**記録は、退会でアカウントを消しても残す**必要があります（残さないと、退会して入り直すだけで2回目が使える）。
そのため、どの契約先にも属さない表に持ちます（§5-2）。

**体験中に「前に体験したお店」を紐付けたとき（Q4）**：

1. **確認の画面を出す。「有料に切り替えて紐付ける」を選んだときだけ、体験を終えて請求する**（**決定**。Q4）
2. 記録だけして、体験は続ける（抜け道になる）
3. 紐付けできないようにする（そのお店を使いたい人が困る）

いまは店舗の編集画面（`StoreEditModal`）がブラウザから直接 DB を書き換えているので、判定のために**サーバーの処理を通すよう作り直します。**

### 3-5. 体験中の管理画面

- **トップに「無料体験 残り○日（○月○日まで）」**。カードを登録した時点で「残り14日」から数える
- **先に動く数字を目立つように出す**。LP が約束している3つは必ず出す：

| 数字 | 元のデータ | LP の約束 |
|---|---|---|
| 二次元コードが読み取られた数 | `page_views` | ○ |
| アンケートの回答の数 | `survey_responses` | ○ |
| Google の投稿画面を開いた数 | `conversion_events`（`opened_google`） | ○ |
| お店にだけ届いた声 | `survey_responses`（Google に進まなかった回答） | —（あると手ごたえが伝わる） |

  体験中は「カードを登録した日から」の数を出す。**Google に実際に投稿された数は出さない**（取得していない。LP の FAQ と同じ）
- **カードを登録した直後は、印刷して置くところまで案内する**：「今日置けば、14日間まるごと試せます」→ 印刷用のデータをダウンロード → 置き方
- **残り3日から**、カウントダウンを警告の色にする（旧 §5-2 の「残り3日で警告色」を引き継ぐ）
- 画面の形は Figma から作る（§6。旧 §5-2 の Figma「12 トライアル期限 / Trial」は、カードなしの体験を前提にしているので作り直す）

### 3-6. お知らせのメール（Q8）

| いつ | 何で送るか | 中身 |
|---|---|---|
| **7日目**（Q8 で10日目から前倒し） | 定期実行（§8） | ここまでの結果（§3-5 の数字）と、残りの日数 |
| **3日前** | Stripe の `customer.subscription.trial_will_end`（体験が終わる3日前に Stripe が送ってくる知らせ） | 終わる日・その日から払う金額・解約のしかた（体験の最終日まで使える）・ここまでの結果 |

- メールは **Resend からアプリが送ります**（`lib/email/send.ts`）。Stripe にも体験の終わりをお知らせするメールの設定があるが、
  文面をこちらで決められないので**使わない**（二重に届かないよう、Stripe 側は切っておく）
- **同じメールを2回送らない。** 定期実行も Webhook も、同じ知らせが2回来ることがある。送ったことを記録する（§5-2）
- 10日目（登録から9日後）だと3日前（登録から11日後）と2日しか離れないので、**7日目（ちょうど半分）に前倒しした**（Q8）

### 3-7. 体験中の解約（Q7）

- 解約は Stripe のカスタマーポータルで行い、**「期間の終わりに解約」**にする（天真の設定作業。§15）。
  体験中に解約すると、体験の最終日まで使えて、**請求は一度も起きない**（Stripe の仕様）
- 解約を予約したら、管理画面に「解約済み。○月○日までお使いいただけます」と出す（カウントダウンの代わり）。
  予約は取り消せる（ポータルの「解約をやめる」）

**解約の理由（1問）を聞く場所**：

1. **Stripe の解約画面の「理由」の機能**（**決定**。Q7）。どこから解約しても必ず聞ける。選択肢は Stripe が決めた8つ
   （高い・機能が足りない・ほかのサービスにした・あまり使わない・対応に不満・使い方が難しい・品質が期待以下・その他）。
   答えは Webhook（`customer.subscription.updated` の `cancellation_details`）で受けて記録する
2. アプリの中で聞いてから、解約の画面へ送る。選択肢を自由に決められる（効果が見えなかった・高い・手間・ほかのサービスにした・その他）。
   ただし解約の入口がポータルにもあるので、**そこから解約した人には聞けない**

体験から有料に進んだ数・解約の数と理由は、**20〜30店たまったら見直す**ために、運営が見られるようにする（まずは Supabase の管理画面から）。

### 3-8. 体験のあと（Q5）

| 状態 | Stripe | こちら |
|---|---|---|
| 請求が通った | `invoice.paid` | 有料期間。通常どおり |
| 請求が通らなかった | `invoice.payment_failed`（Stripe が何日かおいて請求し直す） | **未払い（`past_due`）。止めない**（旧 §4 の決まりのまま）。管理画面に警告を出す |
| 再請求が尽きた・解約した期間が終わった | `customer.subscription.deleted` | **お休み**：管理画面は見るだけ、アンケートはお休み、データは残す |

**Q5**：体験のあとの**初回の請求**が通らない場合は、「一度も払っていない相手」になります。
旧 §5-2 は「一度も払っていない相手は止める」でしたが、今回はカードを登録済みなので、**未払いの決まり（止めない）のまま**にし、
Stripe の再請求が尽きて解約になった時点でお休みにします（決定。Q5）。再請求の回数と期間は Stripe の管理画面の設定です。

**お休みのとき**

- 管理画面は**見るだけ**：これまでの回答・集計は見られる。設定の変更・店舗の追加・二次元コードと卓上POPの発行はできない。
  画面の中央に「カードを登録すると再開できます（データはそのまま残っています）」
- 来店客側：「このアンケートは現在お休みしています／ご協力ありがとうございました」だけ（旧 §5-2 の案C「店のせいに見せない」のまま）。
  **停止の理由も、GOOD REVIEW の名前も出さない**。見た目は v5 の「お知らせの紙」（案B。`feat/demo-v5-ask` の `V5PausedNotice`）。
  いまの本番の画面の見た目に合わせるかは、実装のときに決める
- 再開：もう一度カードを登録すると再開する。**体験は付かない**（2回目の判定。§3-4）

> **8/24 の「解約されても店舗は止めない」（旧 §4）は上書き。** 止めないのは未払い（`past_due`）のときだけ。

### 3-9. 半年使われないときのデータ削除（Q6）

**削除は取り消せません。** 決めたこと（Q6）：

| 項目 | 決定 |
|---|---|
| 対象 | お休み中の契約先だけ（有料・体験中・未払いの契約先は消さない） |
| 「使われない」の数え方 | **お休みになったあと、最後に管理画面にログインしてから180日**。ログインすれば数え直す |
| 消すもの | 回答と集計の元データ（回答・回答のタグ・Google への送客の記録・読み取りの記録など） |
| 残すもの | アカウント・契約先・店舗・アンケート項目などの設定（カードを登録し直せば、同じ二次元コードのまま再開できる） |
| 前もってのお知らせ | 削除の**30日前と7日前**にメール |
| 規約 | 利用規約とプライバシーポリシーに書く（§13）。いまの規約（第9条）は「退会と同時にデータを削除」しか書いていない |

実装では、消す前に**消す対象を数えて記録**し、テスト用の契約先で何度も確かめてから本番に入れます。

### 3-10. 営業経由の契約先

`scripts/create-tenant.mjs` で作る契約先は、**いままでどおり体験なし**（`trial_ends_at` は空、`billing_status = 'none'`）。
カードの関門も出しません（§3-2）。運営が Supabase 上で店舗枠を手で管理します（§4）。

**本番に、カードなしで体験中のアカウントはありません**（2026-09-28 天真が確認）。移行の対応は要りません。

## 4. 店舗枠の正はどちらか

**Stripe が正です。** 「決済されたぶんだけ枠がある」という向きにします。

- 店舗枠の実体は今までどおり `tenants.store_quota`（`supabase/0009`）
- ただし Stripe に繋がっている契約先では、**この値は Stripe からの通知で書き換わる**。
  画面や API から直接増やすことはしない
- **Stripe に繋がっていない契約先**（`billing_status = 'none'`。洋輔さんの検証用アカウント・営業経由の契約先など）は
  今までどおり、運営が Supabase 上で `store_quota` を手で増やす

この二重運用は意図したものです。**カードを登録していない相手にも製品を渡せる**必要があるためです
（検証・デモ・無償提供）。

**申し込みで選んだ店舗数**は `store_quota` の初期値になり、カードを登録して契約を作るときの**数量**になります
（2店舗なら、スタンダード×1＋追加店舗×1）。体験中に増やした分も、体験が終わった日にまとめて請求されます（§2）。

### ⚠ 枠は、いま使っている店舗数を下回らせない（2026-08-24 追加）

「Stripe が正」を素直に実装すると、**運営が手で枠を増やしていた契約先が、
あとからカードを登録した瞬間に枠を失います。**

> 例：夙川店のテナントは運営が手で `store_quota = 3` にしている。
> ここでカードを登録して「基本プラン（1店舗込み）」の契約が作られると、
> Stripe からの通知で枠が **3 → 1** に書き換わる。
> 既存の3店舗は消えないが枠オーバーになり、以後1店舗も追加できなくなる。

これは実運用で必ず起きる事故なので、二重に防いでいます。

| # | 場所 | やること |
|---|---|---|
| 1 | 契約を作る処理（§3-3） | **いまの枠と同じ数で契約を作る。** 3店舗使っているなら3店舗ぶん払う |
| 2 | `/api/stripe/webhook` | 枠を書き込むとき、**いま使っている店舗数を下回らせない**（保険） |

2 が働くと「払っていない店舗が使えてしまう」状態になりますが、それは未払いと同じ扱いで、
人が連絡して決めます。**画面が壊れて店舗を追加できなくなるほうが害が大きい**という判断です。

## 5. データベースの持ち方

### 5-1. いまある列（`supabase/0013`・`0014`）

**利用者からは書き換えられません。** `supabase/0009` の
`revoke insert, update, delete on tenants from authenticated` がそのまま効くため、
お支払いの列は読み取り専用です。書き込むのは Stripe からの通知を受ける処理（service_role）だけです。

| 列（`tenants`） | 中身 |
|---|---|
| `stripe_customer_id` | Stripe 側の顧客ID（`cus_...`）。一意 |
| `stripe_subscription_id` | Stripe 側の契約ID（`sub_...`）。**解約して期間が終わったら空にする**（§12 の3） |
| `billing_status` | `none` / `active` / `past_due` / `canceled`（→ `trialing` を足す。§5-2） |
| `billing_current_period_end` | 今の請求期間の終わり。画面の「次回のお支払い」に出す |
| `trial_ends_at` | 体験の終わり。**2026-09-28 から、Stripe の契約の `trial_end` を Webhook で書く**（申し込みの時点では空） |

`billing_status` の意味（改訂後）：

| 値 | 状態 | 管理画面 | 来店客のアンケート |
|---|---|---|---|
| `none` | カード未登録（申し込み直後、または営業経由） | 使える。二次元コードと店舗枠の追加の手前でカードの登録へ（営業経由は関門なし） | 動く |
| `trialing` | 無料体験中 | 通常表示＋カウントダウン | 動く |
| `active` | 有料期間 | 通常表示 | 動く |
| `past_due` | 請求が通らなかった | 警告を出す。**止めない** | 動く |
| `canceled` | 解約して期間が終わった・再請求が尽きた | **見るだけ**（お休み） | **お休み** |

### 5-2. 足すもの（Q9。1〜4は承認済み、5は追加の確認待ち）

`supabase/` に1機能1ファイルで足します。既存のファイルは書き換えません。

| # | 何を | なぜ |
|---|---|---|
| 1 | `tenants.billing_status` に `trialing` を足す（check 制約の作り直し）。`tenants.billing_cancel_at`（解約の予約日）を足す | 体験中と、解約を予約した状態を画面に出すため。いまは体験中も `active` に丸めている |
| 2 | **2回目の判定の記録**（例：`trial_claims`。種類＝カード／メール／お店、ハッシュ、記録した日） | 退会でアカウントを消しても残す必要がある。**どの契約先にも属さない表**なので、`-- tenant-check-allow: 理由` を付けて tenant チェックの例外にする。**RLS を有効にし、ポリシーを作らない**（ログインした人からは読み書きできない。サーバー＝service_role だけが使う） |
| 3 | **お知らせを送った記録**（例：`billing_notices`。契約先・種類・送った日。同じ組み合わせは1回だけ） | 7日目・3日前・削除の前のメールを2回送らないため。`tenant_id` と RLS あり |
| 4 | **解約の理由**（例：`cancellation_feedback`。契約先・理由・自由記入・日時） | 20〜30店たまったら見直すため。`tenant_id` と RLS あり |
| 5 | **`tenants.card_required`**（申し込みから来た契約先の印。既定は `false`。`/api/signup` で作るときだけ `true`） | Q2（公開アンケートも止める）で必要になった。いまは申し込みから来た契約先も営業経由の契約先も `billing_status = none` で見分けられず、`none` を一律に止めると**いま動いている営業経由のお店のアンケートまで止まる**。既定を `false` にするので、既存の契約先は何も変わらない |

> 2 はハッシュだけを持ち、メールアドレス・カード・お店の ID をそのまま持ちません。
> Supabase は「RLS を有効にしてポリシーが無い表」をログインした人から読むと、**エラーを出さずに空で返します**。
> この表ではそれが狙いどおりの振る舞い（サーバーだけが読む）。

## 6. 画面と導線

設定 → お支払い（`/admin/settings/billing`。Figma `73:1399` PC / `75:1862` SP）はいまのまま使い、次を足します。

| 画面 | 中身 |
|---|---|
| カードの関門 | 二次元コード・卓上POP・店舗枠の追加の手前。「カードを登録して無料体験を始める」 |
| カードの登録の前の画面 | 料金（明細と合計・税抜）、「今日から○月○日まで無料」「○月○日から月額○円」、「体験中に解約すれば料金はかかりません」、「無料体験は1つのお店・1枚のカードにつき1回」 |
| 対象外の確認 | 2回目のとき。理由と今日の金額、「有料で始める／やめる」 |
| 体験中のトップ | カウントダウンと、先に動く数字（§3-5） |
| 登録の直後 | 「今日置けば、14日間まるごと試せます」→ 印刷用のデータ → 置き方 |
| 解約の予約中 | 「解約済み。○月○日までお使いいただけます」 |
| お休み中 | 見るだけ。中央に「カードを登録すると再開できます」 |

**Figma から作ります**（Q12）。design-rules どおり、**先に流れを文章で合意し、画面は3案**、PC と SP の対で作ります。
旧 §5-2 の Figma「12 トライアル期限 / Trial」（残り7日・3日の帯、期限切れで閲覧のみ）はカードなしの体験が前提なので、
下敷きにしつつ作り直します。

### 表示に使う情報は Stripe から都度取りに行く

カードの下4桁・ブランド・請求履歴は、**データベースに保存しません。**
お支払い画面を開いたときに Stripe へ問い合わせて、その場で表示します。

- 保存すると、Stripe 側で変更されたときに**古い情報を出し続ける**（実物と食い違う）
- お支払い画面は頻繁に開く画面ではないので、都度の問い合わせで速度の問題は出ない
- 問い合わせに失敗しても画面は壊さない。その欄だけ「取得できませんでした」にする

### 「契約済みか」を顧客IDで判定しない（2026-08-24 の事故）

**Stripe の顧客は、カードを登録する前に作られます。** 決済画面を作る時点で必要になるためです。

そのため「顧客IDがあるか」で契約済みを判定すると、**登録が途中で失敗した契約先は
顧客IDだけが残り、カードが無いのに「登録済み」と誤判定されます。**
実際に「お支払い方法を登録する」が画面から消え、先へ進めなくなりました。

**判定は契約（`stripe_subscription_id`）と `billing_status` で行います。** 解約して期間が終わった契約先は
`stripe_subscription_id` を空にし、`canceled` にするので、もう一度「カードを登録する」が出ます（§12 の3）。

あわせて、決済画面を作る前に **Stripe 側にも契約が無いかを問い合わせています。**
DB の値は Stripe からの通知で入るため、通知が届かない・遅れている間は
「契約が無い」ように見え、もう一度押すと契約が二重になって二重に請求されるためです。
見つかった場合は DB に書き戻して、画面の表示も回復させます。

## 7. サーバー側の処理

| 経路 | 役割 |
|---|---|
| `POST /api/admin/billing/checkout` | メールとお店で先に判定し、**setup モード**の Checkout（カードを預かるだけ）のURLを作って返す（§3-3） |
| （新）カード登録の戻り先 | 判定して契約を作る（体験あり）／対象外の確認を出す。Webhook と同じ処理を冪等に呼ぶ |
| （新）`POST /api/admin/billing/start-paid` | 対象外の確認で「有料で始める」を押したとき。体験なしで契約を作り、今日の分を請求する |
| `POST /api/admin/billing/portal` | カード変更・請求履歴・**解約**の画面（カスタマーポータル）のURLを作って返す |
| `POST /api/admin/billing/quota` | 店舗枠を +1 する。**体験中は差額を請求しない**（§2） |
| `POST /api/stripe/webhook` | Stripe からの通知を受けて DB に反映する。**唯一 `store_quota` を書き換える場所** |
| （新）`GET /api/cron/...` | 定期実行（§8）。`CRON_SECRET` で守る |

### Webhook が受け取る通知と、やること

| 通知 | やること | 状態 |
|---|---|---|
| `checkout.session.completed` | subscription モード（旧）：顧客IDと契約IDを保存。**setup モード（新）：カードの指紋で判定し、体験ありなら契約を作る** | あり（setup の処理を足す） |
| `customer.subscription.created` / `updated` | 数量から店舗枠を計算して `store_quota` に反映。`billing_status`（`trialing` を分ける）・次回請求日・`trial_ends_at`・解約の予約（`cancel_at`）・**解約の理由**（`cancellation_details`）を更新 | あり（中身を足す） |
| `customer.subscription.deleted` | `billing_status = 'canceled'`、`stripe_subscription_id` を空に。**枠は減らさない**（減らすと店舗が消えたように見えるため） | あり（契約IDを空にする処理を足す） |
| `customer.subscription.trial_will_end` | 3日前のメール（結果つき） | **新しく受ける**（天真の設定作業。§15） |
| `invoice.paid` | 有料期間に入った・更新されたことを記録する（未払いからの回復も） | **新しく受ける**（§15） |
| `invoice.payment_failed` | `billing_status = 'past_due'` | あり |

**通知は必ず署名を検証します**（`STRIPE_WEBHOOK_SECRET`）。
検証しないと、誰でも「支払いが済んだ」という嘘の通知を送って店舗枠を増やせてしまいます。

**同じ通知が2回届くことがあります**（Stripe の仕様）。どの処理も「同じ通知を2回受けても
結果が変わらない」形（＝上書き）で書きます。数を足し算しません。メールは送った記録（§5-2 の3）で2回目を止めます。

**通知と契約先の結び付けは、Stripe の顧客ID（`stripe_customer_id`）で行います。** メタデータ（`tenant_id`）は予備です（Stripe の推奨）。

## 9. 鍵が入っていないときの振る舞い

`STRIPE_SECRET_KEY` が設定されていない環境では、**課金の導線を出しません。**
店舗枠の追加は、今までどおりの**申し込み**（`store_quota_requests`。`supabase/0011`）のままにし、
**カードの関門（§3-2）も出しません。**

こうする理由は2つあります。

1. 鍵が無い状態で押せてしまうと、押した人にはエラーの理由が分からない
2. Stripe を入れる前に契約が始まる可能性がある（洋輔さんの検証がまさにこれ）

**`supabase/0011`（申し込みの表）は残します。** Stripe に完全移行するまでの間、
両方の運用が並走するためです。

## 11. Managed Payments は使わない（2026-08-24 天真の決定）

**Managed Payments** は、Stripe が「販売事業者」として表に立ち、消費税の計算・申告・納付を
代行する仕組みです。**使いません。販売事業者は株式会社UTUTU のままにします。**

| 理由 |
|---|
| `/terms`・`/privacy` が「提供者＝株式会社UTUTU」で書かれており、そちらと食い違わせないため |
| 請求書・領収書を UTUTU 名義で出すため |
| 国内の実店舗向けのため、越境販売の税務を代行してもらう恩恵が薄いため |
| 手数料が上がらないため |

**⚠ Stripe アカウント側の既定は「有効」です。** そのため決済セッションを作るときに
明示的に切っています（`managed_payments: { enabled: false }`)。切らないと商品ごとの
税コード登録が必須になり、`this product tax code is ineligible for Managed Payments`
で決済を作れません（2026-08-24、本番で実際に起きました）。**setup モードの Checkout でも同じように切る。**

方針を変えて Managed Payments を使う場合は、**利用規約の「提供者」の記載と、
請求書の発行元名義の整合を先に確認すること。**

## 14. 確かめ方（本番の契約先に触る前に）

- Stripe の**テストモード**（本物のお金は動かない）と **Test Clocks**（＝日付を進めて、7日目・3日前・15日目をすぐに起こす道具）で確かめる。
  テストのときだけ、新しく作る Stripe の顧客を Test Clock に付ける仕組みを入れる（本番のキーでは動かない）
- **テスト用の契約先**（`npm run tenant:create`）で一周する：申し込み → カードの関門 → カードの登録（0円）→ 二次元コード → 7日目のメール → 3日前のメール → 15日目の請求 → 解約 → お休み → 再登録（体験なし）
- **支払いの失敗**（8月は試せていなかった）：通らないテスト用のカードで15日目の請求を失敗させ、未払い → 再請求 → 解約 → お休み まで
- **2回目の判定**：同じカード・同じメール・同じお店で、それぞれ体験なしになること。体験中に前のお店を紐付けたときの確認の画面
- **体験中の店舗の追加**：差額の請求が出ないこと。15日目に増えた数量で請求されること
- **退会**：Stripe の契約が止まること
- 課金は、本番の契約先に触る前にテスト用で一周する（CLAUDE.md と過去の反省）

## 16. やらないこと（今回の範囲外）

| やらないこと | 理由 |
|---|---|
| 銀行振込・口座振替 | カードのみで開始する決定（§1-1）。断られたら足す |
| プランの変更（上位・下位プラン） | プランが1つしか無い。複数になってから |
| 日割り計算の作り込み | Stripe の既定に任せる（有料期間の増加は差額を即時請求、体験中は請求しない） |
| 未払い（`past_due`）でサービスを止める処理 | 人間が連絡して決める。止めるのは解約して期間が終わったときだけ（§3-8） |
| 請求履歴の4件目以降・領収書PDFの自前表示 | Stripe の画面に任せる。直近3件だけ Figma どおりに出す（§6） |
| 有料期間の解約の条件（最低利用期間など） | LP も「整えているところ」のまま。決まったら、この文書と LP を直す |
| 店舗が2つ以上ある人が、お店・メール・カードをすべて変えて2回目を使うこと | 防がない（天真の判断。§1-3 の7） |
