**「接客」「待ち時間」といったアンケート項目ごとの数字はどこにも出ていない。** それを見る画面。

## 1. 合意済みの決定（2026-08-22）

| 論点 | 決定 | 理由 |
|---|---|---|
| 集計の単位 | **1店舗ずつ** | 店舗ごとにアンケート項目を編集できるため、横並びに足し算すると「別の項目を合計する」事故が起きる |
| 画面の置き場 | **サイドバーに「集計」を新設** | トップと回答一覧の間。独立した画面なので広く使え、コーチマークも出しやすい |
| DBの変更 | **不要** | 回答と項目は `response_tags`（`supabase/0001`）で正規化済み。`store_tags` と結合すれば集計できる |

**未決（天真の判断待ち）**

1. **器** … 案A（横棒ランキング）／案B（表）／案C（カードのグリッド）
2. **前期比を出すか** … 案Bだけが最初から列を持っている
3. **項目を押したときの行き先** … いまの案は「その項目が付いた回答だけの一覧」（`/admin/responses?tag=…`）

## 2. 画面の中身（3案とも共通）

| 出すもの | 中身 |
|---|---|
| 期間 | トップ・回答一覧と同じ（直近7日／14日／今月／3ヶ月／任意）。`lib/admin/period.ts` を使う |
| 店舗の切り替え | `Loop / Select`。1店舗ずつ見る |
| 良かった点 | 項目ごとの「選ばれた回数」「回答数に対する割合」 |
| 改善点 | 同上（★1〜3 の回答から集める） |
| 注記 | 「選んだ項目ごとに集計されます。あとから追加・削除できますが、項目を変えるとその前後の数字は分けて数えられます」 |

**注記は必ず出す。** `docs/specs/onboarding.md` 1章で「3箇所で伝える」と決めた、その3箇所目にあたる。

### 割合の分母

- 良かった点 … **★4〜5 の回答数**
- 改善点 … **★1〜3 の回答数**

★4〜5と★1〜3では選べる項目の語彙が違う（`store_tags.category` が `good` / `improve`）ため、
分母を混ぜない。合計回答数で割ると、改善点の割合が実態より小さく見える。

## 4. 状態の一覧

| 状態 | 出るとき | 出すもの |
|---|---|---|
| 通常 | 回答がある | 上記 |
| 空（0件） | その店舗にまだ回答が無い | 「まだ回答がありません」＋二次元コードの案内 |

| エラー | 取得失敗 | 「読み込めませんでした」＋再試行 |
| 削除確認 | — | **この画面に削除操作は無い** |

## 5. 器の3案

Figma の `MTG` ページ、`Agg-A` / `Agg-B` / `Agg-C`（x=12000〜, y=2800）。
中身（項目・数字・注記）は3案とも揃えてあり、**器だけが違う。**

| 案 | 形 | 強いのは | 弱点 |
|---|---|---|---|
| A | 横棒ランキング | 1店舗を毎週見る店長 | 前期比を足すと窮屈になる |
| B | 表 | 複数店舗を並べて見る本部 | スマホでは横に切れる。SPは別の形が要る |
| C | カードのグリッド | 現場でスマホから見る店長 | 縦に長い。項目10個超で一覧性が落ちる |

## 6. 実装するときの注意

- **新しいSQLは要らない。** `survey_responses` × `response_tags` × `store_tags` の結合で出せる
- 集計は `lib/admin/queries.ts` に足す（`getStoreSummaries` と同じ、ログイン中セッションのクライアントを使う。
  RLSで tenant_id が効く）
- **回答が付いた項目は消せない**制約（`response_tags.tag_id` が `on delete restrict`）がある。
  この画面を作るときに `store_tags.archived_at`（消さずに隠す）を再検討する、と決めてある
  （`docs/specs/onboarding.md` 1章）
- 期間の指定は `lib/admin/period.ts` の `PERIOD_PRESETS` をそのまま使う。独自の期間を作らない
