## 1. 一文の定義

> **v4 は、一文字も書かずに4タップで終われる道を既定に置き、書きたくなった人にだけ本文欄を渡し、
> 書いていて手が止まった人にだけ「本人が書いた語しか使っていない1文」を灰色で差し出す設計です。**

「選別することなく、選択させる」（2026-08-26 天真、洋輔さん承認）を、**書く／書かないにも広げます。**
店が選り分けるのでもなく、AIが代わりに書くのでもなく、**書かないことも選択肢の1つ**にします。

## 2. v3 から何が変わるか（対比表）

| | v3（いま `/demo` で動いているもの） | **v4（この仕様）** |
|---|---|---|
| 画面の数 | intro / questions / selfwrite / summary / destination / offer / draft / store / done の **9フェーズ** | **本編3画面＋出口1画面＋完了1画面** |
| 本文欄の手前の問いの数 | 実質6〜9問（★・来店回数・領域・品・品の感想・良かった点・気になった点・AI追質問 最大2問） | **2問**（★／話題タグ）※Survicate の 2〜3問 86.8% の帯 |
| Google完走までの最短タップ | **21タップ**（全質問経路）／4タップ（自分で書く経路） | **4タップ**（全員に開かれた既定の経路） |
| 文章を誰が書くか | AIが全文（3〜4文）を生成し、本人がコピーする | **本人。書かない選択も完走になる** |
| AIが出す量 | 全文 | **1文。しかも助詞と句読点だけを補ったもの** |
| AIに渡す材料 | 選んだタグ全部（★は渡していない） | **本文欄に本人が打った文字列だけ**（タグも店名も渡さない） |
| AIが呼ばれる回数（1周） | choices ×2・followup ×1（＝**押さなくても自動で走る**） | **0回が既定。**「文にする」を押したときだけ1回 |
| AIが落ちたとき | （本番側）定型文にフォールバック | **何も出さない**（エラー文言も出さない） |
| 文体切替・絵文字・別の言い方 | あり | **全廃** |
| 「今日の感想」の器（KansouPanel） | 画面下に常時（390pxの縦を約220px占有） | **廃止** |
| 吸い込み演出（review-fly） | あり | **廃止**（器が無くなり着地点が消えるため） |
| 章の進捗バー（CHAPTERS） | あり（4章・「あと◯章」） | **廃止**（画面が3枚なので進捗を出す意味がない） |
| ★の扱い | 集計専用（AIに渡さない） | **同じ。集計と低評価アラートにのみ使う**（構造を壊さない） |
| 届け先 | 全員同一の2枚（案I） | **同じ。さらに出口のタップ数まで同数にする** |

**捨てるものが多いのは意図的です。** 作業の大半は削除で、削除は工数が読めます（審査③）。

## 3. タップ数の数え方（3案・v3と統一する）

**画面上の要素を指で触った回数だけを数えます。**

- キーボードの打鍵は数えません（何文字書くかは本人の自由なため）
- OSキーボードのマイクのタップは数えません（アプリ外の操作のため）
- **ソフトキーボードを閉じる操作は、本文欄を使った経路でのみ1タップとして数えます**（安全側）
- v3 の21タップも同じ数え方です（`docs/strategy-2026-09-13.md` §4-1）

| 経路 | タップ数 | v3比 |
|---|---|---|
| **最短・Googleへ**（何も書かない） | **4** | 21 → 4（**19%**） |
| **最短・お店へ**（何も書かない） | **4** | ― |
| タグを1つ選び、自分で書いてGoogleへ（AI未使用） | 7 | ― |
| **最長**（タグ1・本文を書く・AIの1文を採用・Googleへ） | **8〜9** | 21 → 9（43%） |

> 出口のタップ数をGoogle側とお店側で**同数（4）に揃えている**のは意図です。
> 案I（洋輔さん承認済み）の成立条件は「2枚の扉の重さが同じであること」で、
> それを文言ではなく**数えられる形**で担保しています（審査①・審査③が3案で唯一評価した点）。

**⚠ 4という数字は設計上の下限であって、完走率が上がる証拠ではありません。**
strategy 5-3 条件4（5人テストと3店舗の実測）を通すまで、これは「勘で削った」状態です（§10・§12-1）。

### S1 評価（入口を兼ねる）

**目的：** QRを読んだ直後の1枚目。v3の入口画面（「はじめる」）を廃止して★と統合し、
開いた瞬間に1タップ目が押せる状態にする。全員から1タップと1画面ぶんの読む量を無条件に削る。

**画面に出る文言（そのまま）**

```
（ヘッダ）YORKYS BRUNCH 夙川

今日はいかがでしたか？

タップだけで終わります。書くのは自由です。

［ とても満足 ］
［ 満足 ］
［ ふつう ］
［ やや不満 ］
［ 不満 ］
```

**操作**

- 5枚のカードのうち1枚をタップ。タップした瞬間に選択状態になり、**260ms後に自動でS2へ**
  （確定ボタンは出さない。単一選択はタップで進むのが v2 §2-1 で決めた「軽さの正体」）
- 進捗バー・章表示・所要時間表示は出さない（画面が3枚しかないため）

**次に進む条件：** ★が1つ選ばれたら自動遷移。★はこのフロー唯一の必須項目。

**押し間違いの救済（審査①の must_fix）**
自動遷移そのものは維持しますが、**S2の最上部に「今日の評価：満足　変更」の1行を常時置きます**（§S2）。
取り消せることが次の画面に見えていないと、誤タップが離脱ではなく**不信**に変わるためです。

**タップ数：1**

**使う部品：** 既存 `CardList`（`components/demo/DemoSurvey.tsx:1335`）＋ `RATING_CHOICES`（`lib/demo/survey-data.ts`）。
**新設：** 見出し2行のブロックのみ。**削除：** `phase: "intro"` と「はじめる」ボタン、`CHAPTERS` 進捗バー。

### S2 話題と、あなたの言葉（1画面）

**目的：** 本文欄の手前の問いをここで打ち止めにする（★と合わせて計2問）。
話題タグは「分類」ではなく **本文欄の問いを決める切替器** として置く（strategy 5-3 条件3）。
書かない人がここで詰まらないよう、**進むボタンを画面下に固定して常時見せる**。

**画面に出る文言（そのまま）**

```
（最上部・1行）今日の評価：満足　　［ 変更 ］

当てはまるものがあれば選んでください
選ばなくても進めます。

［ 料理 ］［ ドリンク ］［ 接客 ］［ 店内の雰囲気 ］［ 待ち時間 ］［ 値段 ］［ 清潔さ ］

─────────────────────────────
あなたの言葉（書かなくても進めます）

［本文欄。プレースホルダ＝選んだタグで差し替わる問い］

単語を並べるだけでも大丈夫です。話しことばのままで大丈夫です。
キーボードのマイクで、話して入れることもできます。
お名前など、個人が特定できることは書かないでください。

　［ 文にする ］　　←  条件を満たしたときだけ現れる
　（押すと、下に灰色の1文が1行）　　　［ もどす ］
─────────────────────────────

（画面下に固定）　本文が空 → ［ このまま進む ］
　　　　　　　　　本文あり → ［ 書けた ］
```

**本文欄のプレースホルダ（例文ではなく問い。1タグにつき3問を用意し、セッションごとに1問を回す）**

| 選んだタグ | 出る問い（3つから1つをランダムに） |
|---|---|
| （未選択） | 今日、何がいちばん心に残りましたか？ ／ 今日、どんなことがありましたか？ ／ いちばん覚えているのは、どの場面ですか？ |
| 料理 | どの料理が、どうでしたか？ ／ 今日頼んだのは何でしたか？ ／ それは、どんな感じでしたか？ |
| ドリンク | 何を飲みましたか？ どうでしたか？ ／ 飲みものは、どんな感じでしたか？ ／ どれを頼みましたか？ |
| 接客 | 接客で、どんなことがありましたか？ ／ どんな場面のことですか？ ／ 何があったか、覚えていますか？ |
| 店内の雰囲気 | 店内は、どんな感じでしたか？ ／ どのあたりが印象に残りましたか？ ／ 席や広さは、どうでしたか？ |
| 待ち時間 | どの場面で、どのくらい待ちましたか？ ／ いつ、どのくらいでしたか？ ／ どこで待ちましたか？ |
| 値段 | 値段について、どう感じましたか？ ／ 何の値段のことですか？ ／ どのあたりが気になりましたか？ |
| 清潔さ | 清潔さについて、どう感じましたか？ ／ どこのことですか？ ／ 何が気になりましたか？ |

> **なぜ1タグ3問を回すのか（審査②の must_fix）：** 同じ店で同じ問いが100回出ると、
> 答えの話題の分布が問いの形に寄ります。3問を回すだけで、この収束が薄まります。
> **AIは一切呼びません**（静的なテーブル＝待ち時間ゼロ）。※問い文は承認項目 A-3。

**操作**

1. **「変更」**（44px以上）を押すとS1に戻る。★の選択は保持されている
2. **チップ**はタップで即トグル。複数選択可・すべて任意。**「選び終わった ↓」の確定タップは要求しない**
   （同じ画面に主ボタンが常時見えているため）。⚠ この判断は実機未検証です（§12-2）
3. 複数選んだときは、**最初に選んだタグ**の問いをプレースホルダに出す
4. **本文欄**はタップでフォーカス。音声はOSキーボードのマイクでそのまま入る（自前実装しない）
5. **「文にする」**は、本文が6文字以上・入力が800ms停止・「。」で終わる文が2つ未満のときだけ、
   欄の直下に静かに現れる（§6）。押すまでAIは1回も呼ばれない
6. **主ボタンは画面下に固定（sticky）** し、常に押せる状態にする（`disabled` にしない）

**⚠ 主ボタンを画面下に固定する理由（審査①の must_fix）**
この案の逃げ道は**見えていて初めて逃げ道**です。チップ7つ＋本文欄＋注意書き＋AIボタンを
390pxのファーストビューに全部収めるのは実測に依存するので、**固定して実測依存をなくします。**
（それでも縦が苦しい場合の代案は §12-5）

**「選ばなくても進めます」を2箇所に置く理由（審査①の must_fix）**
v3・案1初稿では、この一言が**チップにしかかかっていませんでした。**
本文欄が全員に見えている以上、「書きたくない62%」に対して「書かないことが正常だ」と
画面が明示するのは、主ボタンの語（このまま進む）だけでは弱い。だから本文欄にも同じ語を置きます。

**「単語を並べるだけでも大丈夫です」（案2から移植）**
例文を1つも出さずに、要求水準を「文章」から「単語」へ下げる、いちばん安い一言です。

**次に進む条件：** 主ボタンを押したらS3へ。**タグ0個・本文0文字でも進めます。**

**タップ数：1**（最短。何も触らず「このまま進む」）

**使う部品：** 既存 `ChipGrid`（`DemoSurvey.tsx:1396`。negative分岐は使わない）／
`FreeTextField`（`:1468`。**マイクのダミーボタンと `recording` 状態を削除**し `pr-[56px]` を通常paddingへ）／
`ReviewButton`（`components/rating-flow/Button.tsx`）。
**新設：** `lib/survey/topic-questions.ts`（タグ→問い3つの静的テーブル）／
`components/survey/SuggestLine.tsx`（灰色の1文＋タップ採用＋もどす）／
`app/api/survey/polish/route.ts`。

### S3 届け先を選ぶ（全員に完全同一）

**目的：** 案I（洋輔さん承認済み）をそのまま踏襲する。感情や満足度で書かず、**誰が読むか**という用途だけで書く。

**画面に出る文言（そのまま）**

```
この感想の届け先を選んでください

［ Googleマップに投稿する  ／  だれでも読めます ］
［ お店に直接とどける      ／  お店の人だけが読みます ］

どちらを選んでも、ご回答はお店に届いています
```

**⚠ この文言変更は承認項目 A-1 です。** v3は「Googleでみんなに広める／お店の担当者に伝える」で、
**動詞の強さが揃っていません**（広める＞伝える）。用途表記に揃える提案ですが、
**来店客の目に触れる文言**なので、承認が出るまでは v3 の文言のまま実装します。

**操作**

- 2枚のカードは**同じ大きさ・同じ形・同じ余白・同じ書式**（見出し＋1行）
- **並び順は★によらず固定**。v3が★で入れ替えていた点（`review-flow-rationale.md` §8 の未決論点）は、
  順序効果（先に出たほうが選ばれやすい）が「満足度による扱いの差」に当たりうるため、**ここで固定に決着させます**
- どちらかを1タップした時点で遷移（確認を挟まない）

**次に進む条件：** カードのタップ。Google→S4-A／お店→S4-B。

**タップ数：1**

**使う部品：** 既存 `DestinationStep`（`DemoSurvey.tsx:1859`）をほぼそのまま（変更は文言のみ）。

### S4-A Googleへ

**目的：** コピーとGoogleマップの起動を1タップにまとめる。**本文が空の人もここで止まらずに完走させる**
（Googleマップは★だけの投稿を許容しています）。

**画面に出る文言（そのまま）**

```
■ 本文があるとき
この文章で投稿します

［本文ボックス。タップして直せる］

選んだタグはGoogleには送られません。お店にだけ届きます。
コピーした文章は、Googleの投稿画面で貼り付けられます。

［ コピーしてGoogleを開く ］
（押した直後・約1.6秒）文章をコピーしました

［ もどる ］

■ 本文が空のとき
Googleマップを開きます

文章なしで、★だけの投稿もできます。

［ Googleマップを開く ］

［ もどる ］
```

**「選んだタグはGoogleには送られません」の一文は案3から移植。** 店固有の語彙が公開文に並ぶ経路が
構造として存在しないことを、来店客に見える形で宣言します（効果は限定的ですが、書いてあること自体が誠実です）。

**「文章をコピーしました」のトーストは審査①の must_fix。** Googleマップへ飛んだ先で貼り付けるのは
本人の作業なので、コピーされた確証がないまま遷移すると、**最後の1手で落ちます。**

**操作**

- ボタン1タップで、クリップボードへのコピー（本文があるときのみ）と、
  Googleマップ投稿URLを開くことを**同時に**行う。押した直後にS5へ切り替える
- ★・タグ・AI補助の有無は**Google側に一切表示しない**（「AI補助を使いました」ラベルは付けない）

**次に進む条件：** ボタン1タップ → S5。

**タップ数：1**

**使う部品：** 既存 `AutoGrowTextarea`（`:1835`）／`ReviewButton`／
`docs/specs/rating-flow.md` のGoogle直リンクと `place_id` フォールバック。
**新設：** `CopyAndOpen`（`navigator.clipboard.writeText` → `window.open` を1ハンドラにまとめ、トーストを出す）。

### S4-B お店へ

**目的：** 店に何が届くのかを送信前に見せる。Google側と**同じ1タップ**で終わらせ、2つの出口の重さを揃える。

**画面に出る文言（そのまま）**

```
お店にとどく内容

今日の評価：満足
選んだこと：料理／接客　　←  無ければこのブロックごと出さない
あなたの言葉：（本文）　　←  無ければこのブロックごと出さない

［ とどける ］

［ もどる ］
```

**操作**

- 表示のみ。チップの外し直しや文章化はここでは求めない（v3の `summary` 画面は廃止）
- ボタン1タップで送信し、S5へ。**楽観的更新**（先にS5を出し、失敗したときだけ静かに再送）

**次に進む条件：** 「とどける」を1タップ → S5。

**タップ数：1**

**使う部品：** 既存 `ChipGrid` の表示形（読み取り専用の span 版）／`ReviewButton`／
`phase: "store"` のレイアウトを縮小して流用。
**削除：** `store` フェーズの「ひとことを追加する（任意）」欄（本文欄がS2に一本化されたため二重になる）。

### S5 完了

**目的：** 終わりを明示する。追加のタップを一切要求しない。

```
ありがとうございました

（Googleを選んだとき）Googleマップの投稿画面を開きました
（お店を選んだとき）　いただいた内容は、お店の担当者が確認します
```

操作なし。再投稿・シェア・アンケート再開などの追加導線は置かない。**ここに到達したことを「完走」として計測します。**

**使う部品：** 既存 `DoneStep`（`:1900`）。本番ではデモ用の注記行（「これは検証用のデモです」）を外す。

## 5. 白紙の壁をどう越えるか（例文は1つも出さない）

仕掛けを5つ重ねます。**このうち4つは、AIを1回も呼びません。**

1. **本文欄のプレースホルダが常に「問い」である。** タグを選ぶとその話題の問いに差し替わる。
   問いは答えの形を決めませんが、例文は決めてしまいます（strategy 5-3 条件1）
2. **問いは1タグ3問を回す。** 同じ店で同じ問いが並ばない（審査②）
3. **「このまま進む」が画面下に固定で見えている。** 書かないことが正常だと画面が先に言う
4. **「単語を並べるだけでも大丈夫です」「話しことばのままで大丈夫です」**（案2から）。
   要求水準を文章から単語へ下げる。書けない人の大半は語がないのではなく**文にできない**
5. **書き始めたあとにだけ「文にする」が現れる。** つまり**白紙の人にはAIが一度も現れません**

**文字数の目標もカウンターも出しません**（長さが揃うこと自体が、似た文面の一形態です。strategy 5-4）。

## 6. AIの助け — 完全仕様

### 6-1. 呼ばれない経路が既定であること

- 本文欄が空のあいだは**「文にする」ボタンが存在しません**。白紙からAIが文を作る経路は**構造的にありません**
- 最短経路（4タップ）では、AIの呼び出しは**0回**です
- v3にあった `choices`（品ごとの選択肢生成）と `followup`（AI追質問）は**廃止**するので、
  「押していないのにAIが走る」経路が**1つも残りません**（案3が満たせなかった条件）

### 6-2. 起動条件と見え方

| | 内容 |
|---|---|
| ボタンが現れる条件 | 本文が **6文字以上** ＋ 入力が **800ms 停止** ＋ 「。」で終わる文が **2つ未満** |
| ボタンの見た目 | 本文欄の直下、**輪郭だけの小さなボタン**「文にする」。塗りにしない・主CTAの強さを出さない |
| APIが呼ばれる瞬間 | **押したとき、1回だけ** |
| 出るもの | 本文欄の**下**に、**灰色の1文が1行**。本文欄の中身は書き換わらない |
| 採用 | 灰色の文を**タップして初めて**本文欄の中身が置き換わる。その場に「もどす」（1回だけ有効） |
| 失敗・検証落ち | **何も出さない。**エラー文言もローディングの人格演出も出さない |
| 回数制限 | **1セッション3回まで**（サーバー側で数える。ブラウザの申告を信じない） |
| AIに渡すもの | **本文欄の文字列だけ。** ★・話題タグ・店名・メニュー名・業態・過去の回答は渡さない |

### 6-3. 出す1文の性質（ここが v4 でいちばん重要な変更点）

> **助詞と句読点だけを補って、読める1文にする。それ以外は何もしない。**

| してよいこと | してはいけないこと |
|---|---|
| 助詞を補う（「パンケーキふわふわ」→「パンケーキがふわふわで」） | 語尾を変える（「よかった」→「よかったです」）**← v4で禁止に変更** |
| 句読点を打つ | 言い換える（「ふわふわ」→「ふんわり」） |
| 空白・改行を整理する | 続きを提案する／新しい語を足す |
| ― | 誤字を直す（§12-3の未解決） |
| ― | 語の順序を変える |

**例：**
`パンケーキふわふわ 接客もよかった` → `パンケーキがふわふわで、接客もよかった。`

**⚠「語尾を『です・ます』に揃える」を禁止にした理由（審査②が指摘した最大の自己矛盾）**

案1の初稿は整形に「語尾を『です・ます』に揃える」を入れていました。それをやると
**AIを通した文は100件すべてが「〜です。」「〜ました。」で終わります。**
これは、この設計自身が根拠に挙げている Höhne, Gavras & Claassen（Social Science Computer Review, 2024,
n=1,001）の「言い直しやフィラーが残ると長さとリズムにばらつきが出て、それが人間らしさになる」を、
整形仕様で正面から潰す行為です。加えて、語尾の統一は体裁ではなく**公開文の文体の決定**であり、
景表法運用基準 第2・1(2)イ／第2・2(1)オ（**委託を受けた仲介事業者を含む**）の下では、
GOOD REVIEW が決めた語尾で100件が並ぶ事実が**関与の証跡として残ります。**

→ **語尾は本人のまま残します。**

### 6-4. サーバー側の検査（AIの自己申告を信じない）

**形態素解析器（＝文を単語に割って品詞を判定するライブラリ）を使いません。**
理由：このリポジトリの依存に形態素解析は1つも入っていません（`package.json` の依存は
anthropic-sdk / supabase / next / qrcode / stripe の5つだけ）。辞書は十数MBあり、
Vercel の関数に載せる判断が別途発生します。**書いてあるのに実装されない安全装置は、
strategy 4-2 #4 が名指しした「迂回できる飾り」に逆戻りします**（審査②・審査③が共通で指摘）。

**代わりに、文字だけで判定します（案2の `validateParticleOnly` ＋ 案3の2-gram包含を併用）。**

新設 `lib/survey/polish-guard.ts` に、次の6つを順に通します。**1つでも落ちたら候補を捨て、画面には何も出しません。**

| # | 検査 | 内容 | 由来 |
|---|---|---|---|
| 1 | **文字アライン** | 入力と出力を文字単位で並べ、**削除を認めない**（句読点・空白・改行の削除だけ許す） | 案2から |
| 2 | **挿入の制限** | 挿入は**ひらがなのみ、連続2文字以内**、＋句読点・空白。助詞（が・を・に・で・は・も・と・へ／から・まで・ので・のが＝2文字）が通る | 案2から（3文字→2文字に厳格化） |
| 2b | **敬体化の禁止** | 入力に無い「です・ます・ました・でした・ません・ましょう・でしょう・ございま」が出力に現れたら捨てる | ⚠ 2026-09-13 追加（下記） |
| 3 | **語順** | 入力に現れる順序が出力でも保たれているか | 案2から |
| 4 | **2-gram包含** | 助詞・記号を除いた**文字2-gram**がすべて本人の本文に含まれるか（1と2の補助判定） | 案3から |
| 5 | **禁止語・メタ発言** | 既存 `lib/demo/fact-model.ts` の `BANNED_WORDS`（また来たい・美味し・最高 等）と `META_PATTERNS`（申し訳・指示・JSON 等）。入力に無いのに出たら破棄 | 既存資産を転用 |
| 6 | **形と長さ** | 句点が1つ以下／**出力の文字数が入力の1.4倍以内**（絶対値の上限は置かない） | 審査②の must_fix |

> **⚠ 「40字上限」を捨てて相対値にした理由：** 絶対上限は、AIを採った人の文の長さを揃える装置です。
> 「文字数の目標・カウンターを出さない」という方針と矛盾します（審査②）。

> ### ⚠ 訂正（2026-09-13、実装時に必須テストが捕まえた）
>
> 上の表の #2 に「連続2文字以内にすれば**『です』(3)・『ました』(3)** は通らない」と書いていましたが、
> **これは誤りです。**
>
> - **「です」は2文字**（で＋す）。連続2文字の制限を素通りします。
> - **「ました」も通ります。** 入力の「た」と出力の「た」を一致させれば、挿入は「ま」「し」の2文字で済むためです。

> 実装して `npm run survey:guard` を走らせたところ、この2つが**実際に通ってしまいました。**
> そこで **#2b「敬体化の禁止」** を足しました。入力に無い敬体の語尾が出力にあれば、それだけで捨てます。
> これで「語尾は本人のまま残す」が機械的に保証されます。
>
> **あわせて #4（2-gram包含）も直しました。** 「助詞・記号を除いた2-gram」と書いていましたが、
> 助詞を機械的に見分けるには形態素解析が要ります。代わりに**ひらがなを丸ごと落として

> 検査の必須テストは `scripts/polish-guard-fixtures.mjs`（`npm run survey:guard`）。

### 6-6. なぜこの性質なのか（根拠）

| 設計 | 根拠 |
|---|---|
| AIの出力を **1文・灰色・タップして初めて本文** にした | arXiv 2404.00027v3：提案は段落より1文、自動挿入より手動取り込みのほうがオーナーシップ（＝自分が書いたという感覚）の低下が小さい。v3の「押すと全文が出てコピーする」は**3条件すべての逆** |
| AIに渡す語彙を **本文欄の文字列だけ** に限った | arXiv 2601.10236（N=176）：AIが書くとオーナーシップが7段階で0.85〜1.0pt低下。回復した唯一の手段が**本人の文章からの文体アンカリング**で +0.43pt、AI文の採用率も約5pt上昇 |
| **全文生成を廃止** した | Doshi & Hauser, Science Advances 2024（査読済み）：AIのアイデアを与えられた書き手の作品は互いに似てくる。**同じ店の下書きが似るのはプロンプトの粗さではなく構造的必然**で、消す方法はAIが書く量を減らすことだけ |
| AI人格の演出・生成中の文言を入れない | arXiv 2601.10236：擬人化演出ではオーナーシップは回復しなかった。加えて BrightLocal 引用の46%（AIが書いたように見えたら偽レビューだと疑う） |
| 役割を **整形だけ** に絞った | Birdeye（業界最大手）の線引き「代筆して本人のものとして出すのは一線を越える／本人が考えを明確に表現するのを助けるのは信頼を損なわない」。**独自路線ではなく業界標準側** |
| **語尾を本人のまま残す** | Höhne et al. 2024：言い直しやフィラーが残るとリズムにばらつきが出て、それが人間らしさになる。整えると長さとリズムが揃い、まさに「AIっぽく」なる |
| **★をAIに一切渡さない** | Googleポリシー層2「評価やクチコミの**内容に影響を与えようとしない**／特定の内容を含めるよう求めない」＋景表法Q&A Q6「『星5』ではなく推奨するコメントを条件とする場合も同様」。本番プロンプトの「★5なら『また来たい』を含める」がステマ指摘の直接原因（strategy 4-1の実測：3回とも「また来たい」を含み、2回は回答に無い事実を捏造） |
| サーバー側で検査し、レート制限をかける | strategy 4-2 #4/#5：現行の検証層はブラウザ側だけ（＝迂回できる飾り）で、AIの入口は認証なし・上限なし |

## 7. お店に届くもの

### 7-1. 届く4つ

| # | 届くもの | 内容 |
|---|---|---|
| 1 | **★**（1〜5） | 集計・件数の母数・**低評価アラート**に使う。**AIには一切渡らない** |
| 2 | **話題タグ**（0〜7個） | 料理／ドリンク／接客／店内の雰囲気／待ち時間／値段／清潔さ |
| 3 | **届け先**（google / store） | 送客率としてすでにある管理画面トップにそのまま載る |
| 4 | **本人の文章** | S2で書かれた文字列を**そのまま**保存。清書・要約・感情分類をかけない |

**⚠ AI補助を使ったかどうかは、公開側にも店舗側の画面にも出しません（案2から移植）。**
案1の初稿は「内部フラグ」を店舗に届く項目として並べていましたが、
**店主が「これはAIの文だ」と選り分け始めた時点で、「選別することなく、選択させる」が裏口から壊れます。**
入力・AI出力・検査の合否は**非公開の内部ログ**（`ai_polish_logs`）にだけ残し、
§6-4の似すぎ検査と監査にのみ使います。

### 7-2. 店側の見方

主たる見方は **★ × 話題タグのクロス集計**。
「★2の人の6割が『待ち時間』を選んでいる」「★5の人が選んだ話題の1位は『接客』」という粒度です。
v3が目指した品別集計より粗いですが、**全員ぶん・毎回必ず取れます。**

**★だけ付けて帰った人も1件として数え、母数から落としません。**
落とすと、いちばん忙しい時間帯の声が構造的に消えるためです。

### 7-3. 低評価アラート（審査③の must_fix への回答）

strategy 4-2 #7 は「★分岐を廃止すると低評価アラートが静かに死ぬ」と書いていますが、
**v4では★を全員から取り続けるので、`rating <= 3` という現行の発火条件はそのまま成立します**
（`lib/rating-flow/low-rating-alert.ts` の `LOW_RATING_THRESHOLD = 3`）。
変えるのは通知の中身だけです。

- 発火条件：**`rating <= 3`（変更なし）**
- 通知本文に足すもの：**届け先（Google／お店）**、**本文の有無と本文そのもの**、**選ばれた話題タグ**
- 「お店を選んだ人だけ通知する」にはしません（Googleを選んだ★2の人こそ、店が最初に知るべき相手です）

## 8. DB — 既存資産に載せる（審査③の最重要 must_fix）

### 8-1. 何が問題だったか

案1の初稿は `survey_responses` に `topic_tags text[]`（＝タグを文字列の配列で1列に持つ）を足す設計でした。
**これは本番と二重になります。** 本番はすでに正規化された構成（＝タグを別の表に1行ずつ持つ形）で、
その上に管理画面の集計と設定画面が載っています。

| 既存の資産 | 場所 |
|---|---|
| `tags_master`（全店共通のプリセット。9業態ぶん） | `supabase/0001` ＋ `0010`（`business_category`） |
| `store_tags`（店舗ごとのタグ。`tenant_id` ＋ RLS 済み） | `supabase/0005` |
| `response_tags`（回答×タグの中間表） | `supabase/0001`（`0005` で参照先を `store_tags` へ切替済み） |
| 集計の join（`response_tags` → `store_tags`） | `lib/admin/queries.ts:186, 254-286` |
| 店舗別タグ設定画面 | `app/admin/(dashboard)/settings/survey` |

`text[]` にすると、**管理画面の集計が新しいタグを1件も拾わなくなります。**
＝「作ると壊れる」変更です。

### 8-2. v4 でやること（`supabase/0017_survey_v4_topic_tags.sql`・1機能1ファイル）

```sql
-- 1. タグに「話題（中立）」の種別を足す（既存の good / improve は残す）
alter table tags_master  drop constraint if exists tags_master_category_check;
alter table tags_master  add  constraint tags_master_category_check
  check (category in ('good', 'improve', 'topic'));
alter table store_tags   drop constraint if exists store_tags_category_check;
alter table store_tags   add  constraint store_tags_category_check
  check (category in ('good', 'improve', 'topic'));

-- 2. 9業態ぶんの topic プリセットを tags_master に追加（中立語のみ。§9の運用ルール）

-- 3. 届け先を記録する
alter table survey_responses add column if not exists destination text
  check (destination in ('google', 'store'));

-- 4. ★分岐の廃止に伴い、branch を必須でなくする（既存行はそのまま残る）
alter table survey_responses alter column branch drop not null;

-- 5. AI整形の内部ログ（店舗側の画面には一切出さない）
create table if not exists ai_polish_logs (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null references tenants(id) on delete cascade,
  store_id  uuid not null references stores(id)  on delete cascade,
  input_text text not null,
  output_text text,
  guard_result text not null,   -- passed / rejected-align / rejected-similar ...
  created_at timestamptz not null default now()
);
alter table ai_polish_logs enable row level security;
create policy "ai_polish_logs: tenant isolation" on ai_polish_logs
  for all
  using      (tenant_id = (auth.jwt() -> 'app_metadata' ->> 'tenant_id')::uuid)
  with check (tenant_id = (auth.jwt() -> 'app_metadata' ->> 'tenant_id')::uuid);
```

**`tenant_id` ＋ RLS は対で必須**（CLAUDE.md 4章）。`tags_master` は既存の
`-- tenant-check-allow:` コメントの対象なので変更不要です。

### 8-3. 回答APIの変更

`app/api/rating-flow/responses/route.ts` は現在、
`.eq("category", body.branch)` で**★からタグの語彙を選んでいます**（:79）。

- `branch` の送信を任意にし、不一致チェックを外す

**⚠ §8 全体が承認項目 A-4 です。** 列の型変更・制約の緩和はCLAUDE.md 3章の対象です。

## 9. 話題タグの運用ルール（審査②の must_fix — 条文として書く）

現行の7語（**料理／ドリンク／接客／店内の雰囲気／待ち時間／値段／清潔さ**）が中立なのは、
**肯否どちらにも開いているから**です。

> **禁止：話題タグに、良し悪しの方向を持つ語を足さないこと。**
> 「おいしさ」「居心地のよさ」「丁寧さ」のような語を1つ足した瞬間に、
> Googleポリシー層2（**特定の内容を含めるよう求めない**）に触れます。
>
> **判定のしかた：** そのタグ名だけを見て「良かった」とも「悪かった」とも続けられるか。
> 続けられないなら足さない。（○「待ち時間が長かった／短かった」 ×「おいしさが〜」）
>
> **タグの追加・変更は、天真さんの確認事項とする**（来店客の目に触れる文言であり、
> かつ規約上の判定に直結するため）。

同じ理由で、**スタッフ名を聞く問いを作りません**（Googleポリシーが2026年2月に
「スタッフ名を含む依頼」を明文で禁じています）。接客の問いは「接客で、どんなことがありましたか？」
のように、**人名を促さない中立語**にします。

## 14. 未解決の論点（天真さんの判断が要るもの）

> 番号を振ってあります。**それぞれ選択肢と推奨を付けました。**
> 「◯番は（ア）で」のように返してもらえれば進みます。

### 14-1. 4タップは設計上の最短であって、完走率が上がる証拠がない

strategy 5-3 条件4（5人テストと3店舗の実測）が未実行です。
v3の作り込み（吸い込み演出・章立て・品ごとのAI選択肢）を全部捨てる判断を、**実測なしで行っています。**

| 選択肢 | 何が違うか |
|---|---|
| （ア）**先に5人テストだけ回し、v3のまま観察してから v4 を作る** | 遅くなるが、何を削るべきかが分かってから削れる |
| （イ）**v4を作ってから5人テストを回す（段0の計測込み）** | 早いが、削った判断の是非は後から分かる |
| （ウ）v3 と v4 を両方 `/demo` に置き、5人に両方触らせる | いちばん情報が多いが、v3の削除が段5までできず工数+1.5日 |

**推奨：（イ）。** 理由：v3は21タップで、「1分」というPOPの約束と整合していません（strategy 4-1）。
**壊れていると分かっているものを観察するために時間を使うより、直したものを観察するほうが情報の質が高い**と判断しました。
ただし段0（計測）を**必ず先頭に置く**ことが条件です。

### 14-2. 複数選択の「選び終わった ↓」を外したこと

survey-v2 §14 は実機フィードバックから入れたルールです
（「1つ選んだ時点で次が見えると『1つで終わり』と受け取られる」）。
v4 はこれを、**同じ画面に主ボタンがあることを理由に、実測なしで覆しています。**

| 選択肢 | 何が違うか |
|---|---|
| （ア）**外したまま作り、5人テストの観測項目にする**（平均タグ数が1個に張り付いたら戻す） | 最短4タップが成立する。外れていた場合は戻す工数0.5日 |
| （イ）最初から戻す（＝タグを1つでも選んだら「選び終わった ↓」を出す） | 安全だが、タグを触った人の最短が+1タップになる |

**推奨：（ア）。** v4のS2は主ボタンが**画面下に固定**されていて常時見えるため、
v3の「次の質問が視界に入る」状況とは別物です。ただし**これは推論であって実測ではありません。**

### 14-3. AIに誤字を直させるか

strategy 5-4 は「整えるのは誤字と句読点だけ」と書いていますが、
**誤字修正は「置換」＝文字の削除を伴うため、§6-4 の検査1（削除を認めない）と両立しません。**
v4 は誤字修正を**落として**います。

| 選択肢 | 何が違うか |
|---|---|
| （ア）**落としたまま（助詞と句読点だけ）** | 検査が airtight（＝抜け道がない）。誤字はそのまま残る |
| （イ）誤字も直す | 検査1を「削除は1文字ずつ・1文につき2箇所まで」等に緩める必要があり、**抜け道ができる** |
| （ウ）誤字だけ別扱い（辞書ベースの決定論で、AIを通さず直す） | 安全だが、日本語の誤字辞書を持つ工数が別途1〜2日 |

**推奨：（ア）。** 音声入力で書いた文の言い直しやフィラーは、**残っているほうが人間らしい**
（Höhne et al. 2024）ので、誤字も同じ側に置けます。

### 14-4. 本文なしの★投稿が束で立ったときのGoogle側の判定が分からない

「Googleマップは★だけの投稿を許容している」のは事実ですが、
**それは単発の投稿の話で、同一店舗・同一時間帯にツール由来の無記述★が束で立つ場合の説明にはなっていません。**
2026年4月の執行強化（Geminiによる自動検知）がこれをどう扱うかは**一次情報がありません**（審査②）。

| 選択肢 | 何が違うか |
