## 1. 進め方

### 1-1. ピクセルを作る前に、操作の流れを文章で合意する

いきなり Figma を触らない。先に以下を文章で出し、天真の合意を取る。

- 画面遷移（どこから入って、どう戻るか）
- 各画面で人が何をするか
- 状態の一覧（通常／空／0件／エラー／ローディング／確認）

**「作ってから直す」は禁止。** 合意を取らずに作ったものは、作り直しになっても抗議しない。

### 1-2. 案は必ず3つ出す

天真が1案を提示した場合も、**それ以外に2案を足して合計3案**にする。1案だけ出して却下されると、ゼロからやり直しになり時間が倍かかる。

- 3案は**比較できる形**で出す。中身（項目・文言）は揃え、**器だけを変える**
- 各案に「どういう店舗・状況で強いか」を1行添える
- 明らかに劣る当て馬を混ぜない。3案とも本気で作る

### 1-3. 指示されていない次工程に進まない

デザインを頼まれたらデザインまで。**DBスキーマ・実装・マイグレーションには勝手に進まない。**
必要だと思ったら「必要です」と言って止まる。

### 1-4. 判断が要る場面では止まる

仕様に書かれていないことを勝手に決めない。決めた場合は**決めたことを明示**して、いつでも覆せる状態にする。
（例：「項目の入力方式はテキストエリアにしました」→ これは相談すべきだった）

## 2. 作るもの

### 2-1. PC を作るときは必ず SP も対で作る

**例外は「PC版だけ」と明示して依頼されたときのみ。**
GOOD LOOP は来店客が卓上POPのQRから開くので、お客様側は SP が主。
それでも管理画面は PC が主なので、**どちらか片方だけを作って終わりにしない。**

これは `npm run design:figma` が機械的に落とす（サブセクションを作った時点で PC / SP の対が必須になる）。

### 2-2. 必須の状態セット

画面を作ったら、以下のうち**その画面に起こりうるものを全部**作る。1枚だけ作って終わりにしない。

| 状態 | いつ必要か |
|---|---|
| 通常 | 常に |
| 空（データが0件） | 一覧・リストがある画面 |
| 絞り込み結果0件 | 検索・絞り込みがある画面 |
| ローディング | 通信を伴う画面 |
| エラー | 通信・保存を伴う画面 |
| 削除確認 | 削除操作がある画面 |

### 2-3. 既存の共通コンポーネントを使う

ボタン・チップ・タブ・フォーム・モーダルなどを**生の Frame で自作しない。**
既存に無い場合は、自作する前に「無いので作ります」と申告する。

### 2-4. 色は変数から取る。ベタ値を置かない

業態別テーマ（変数コレクション `Loop Theme` ＝9モード）は、**モードを切り替えるだけで
全画面の色が変わる**ことが前提。塗り・線を変数にバインドせずベタ値で置くと、その要素だけ
業態を切り替えても変わらず取り残される。

**スウォッチや仕様書きで HEX 値をテキスト表示する場合、その文字列は、
実際にその要素にバインドされている変数の値と一致していること。**
食い違っていると、実装側がテキストのほうを信じて写し取り、画面に間違った色が出る。
値を変えたら、スウォッチのラベルも同時に直す。

### 2-5. 余白の値

余白・間隔は **Spacing 変数（`space/*`）**を使う。

> **スペーシングを用いるのは将来スケールを変える可能性があるからではなく、
> この数字で組むと美しくなるから。中途半端な数字が交じると崩れていく。**

理由はこれだけである。「あとで一括変更できるから」ではない。
**中途半端な数字が1つ交じると、そこから全体の秩序が崩れていく。**

スケールは以下。

```
2, 4, 8, 12, 16, 20, 24, 32, 40, 48, 64, 80, 96, 112, 128
```

- オートレイアウトの `paddingTop` / `paddingRight` / `paddingBottom` / `paddingLeft` /
  `itemSpacing` / `counterAxisSpacing` が対象
- 変数にバインドしてあれば合格。バインドしていなくても、値がスケール上（および `0`）なら合格
- **10px や 18px のような、スケールに無い値を置かない**

これは `npm run design:figma` が機械的に検出する
（「余白がスケール外です（`itemSpacing=10`）」というメッセージで出る）。
インスタンスの内部は見ない。そちらはコンポーネント側で担保する。

**例外を作りたくなったら、値をずらすのではなくスケール自体を見直す相談をすること。**
「ここだけ10pxにしたい」は、たいてい「スケールに10pxが足りない」か
「隣の要素の余白が間違っている」のどちらかである。

## 3. ファイルの構造

```
ページ（App Design Master など）
└ セクション（機能名 / 日本語名）      ← 最上位。x=0 に揃えて縦積み、間隔100px
   ├ セクション「PC」                  ← 上・左パディング100px
   │  └ フレーム（Template / xxx）     ← 上・左パディング100px、間隔100px
   └ セクション「SP」
      └ フレーム
```

### 3-0. 打ち合わせ資料は `プレゼン` ページに置く

**スライド・提案資料・議事メモは、画面ではない。** `App Design Master` などの
画面制作ページに置かないこと。**`プレゼン` という名前のページを作って、そこに置く。**

`プレゼン` ページは `npm run design:figma` の検品対象から外してある
（`scripts/check-figma.mjs` の `SKIP_PAGES`）。

理由は2つ。

1. スライドは画面の規約（PC/SP の対・セクション色・100pxパディング・余白のスケール）に
   従う必要が無い。従わせても意味が無い
2. **そのまま検品すると、1回の打ち合わせ資料で数百件の違反が積み上がる。**
   ベースラインは「返済の作業リスト」なので、返済する気の無いものを載せると読めなくなる
   （実測：21枚のスライドで構造4件 ＋ 余白908件）

**`99 〜` にリネームする方法では足りない。** `99 〜` は構造検査だけを外すもので、
余白のスケール検査は素通りしない（実測で確認済み）。ページごと外すこと。

### 3-1. パディングは3箇所すべて100px

- 最上位セクション同士：**100px**
- セクション内の PC / SP セクション：**100px**（上下左右）
- PC / SP 内のフレーム：**100px**（上下左右、フレーム同士の間隔も）

### 3-2. セクションの色

階層が目で見て分かる状態を保つ。**色は固定。気分で変えない。**

| 対象 | 色 |
|---|---|
| 大枠（最上位セクション） | `#7E7E7E` |
| 中枠（`PC` / `SP` サブセクション） | `#444444` |

これは `npm run design:figma` が機械的に判定する（構造・パディングと同じ扱いで、必ず落ちる）。

### 3-3. 命名

| 対象 | 形式 | 例 |
|---|---|---|
| 最上位セクション | `英語名 / 日本語名` | `Rating / 評価入力` |
| サブセクション | `PC` / `SP` | — |
| 画面フレーム | `Template / 画面名 幅x高` | `Template / Rating 390x844` |
| モーダル | `Modal / 名前 — PC` | `Modal / 送信確認 — PC` |

### 3-4. セクションにはオートレイアウトが効かない

SP に画面が増えても PC 側は自動でずれない。**放置すると重なる。**
だから 4-1 の整理整頓を毎回やる。

## 4. 完了の定義

作業の最後に、以下が全部済んでいて初めて納品。

### 4-1. 全ページを整理整頓する

作業したページだけでなく、ファイル内の**全ページ**が整理された状態で渡すこと。

- 画面制作（アプリ・Web）のセクションは、必ず PC と SP の2つのサブセクションを持つ。
  構造は ページ ＞ セクション（機能名 / 日本語名） ＞ PC / SP ＞ フレーム の3階層。
  片方だけ作るのは禁止で、「PC版だけ」と明示された場合のみ例外
- セクションの直下に置いてよいサブセクションは PC と SP だけ。それ以外の名前のサブセクションを作らない
- コンポーネントライブラリやガイドラインなど、画面ではないページのセクションはサブセクションを持たなくてよい
- `99〜` で始まるセクションは素材・メモの置き場。構造は問わない
- 各セクションは、中身の外接矩形がちょうど100pxの余白で収まるサイズにする
- セクションは x=0 に揃えて縦に並べ、間隔は100px。**横に並べない**（要素が増えたときに重なるため）
- セクションの色は 3-2 のとおりにする
- ページ直下に浮いたフレームを置かない。置き場が必要なら `99〜` で始まるセクションを作って収容する
- 新しいコンポーネントをセクションに追加したら、必ず下のセクションを押し下げる。広げるだけだと下のセクションが飲み込まれる
- 位置を動かしたら、書き込んだあとに読み戻して確認する。反映されていないことがある

**制作の途中で崩れるのは構わない。終わったときに崩れているのが問題。**

### 4-2. 検品を通す

```
npm run design:figma
```

- **構造・パディング・セクション色**：0件でなければ納品しない
- **今回増えた違反**：0件でなければ納品しない
- **`scripts/figma-check-baseline.json` は空のまま維持する。**
  GOOD LOOP はゼロ件で始めている。`--update-baseline` で違反を握り潰さないこと。
  どうしても登録が必要だと思ったら、登録する前に天真に相談する

### 4-3. スクリーンショットを提示する

作った画面を天真に見せる。**「Figma を見てください」で終わらせない。**

## 6. Figma への書き込みについて

- **明示的に依頼されたときだけ書き込む。** 読み取りは自由
- 既存のコンポーネントを変更するときは、**影響範囲を先に伝える**
- 大きく作り替える前に、元のフレームを複製して残す。破壊的変更をいきなりやらない
- **別のセッションが同じファイルを編集している可能性がある。** 検品が急に落ちたときは、
  自分の変更が原因とは限らない。ベースラインに登録して黙らせる前に、まず状況を確認すること

## 7. トークンの有効期限

`npm run design:figma` は環境変数 `FIGMA_TOKEN`（Figma のパーソナルアクセストークン）を使う。

- **有効期限は 2026-11-01。** 切れると **403** で落ちる。スクリプトのバグではない
- 切れたら Figma で発行し直し、`~/.zshrc` の `export FIGMA_TOKEN="figd_..."` を更新する
- **トークンをリポジトリに置かない。** このリポジトリは public。`npm run secrets` が落とす
