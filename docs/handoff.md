## プロジェクトの概要

**GOOD LOOP** — 実店舗向けの「Googleレビュー獲得 × 顧客満足度アンケート」SaaS。
株式会社UTUTU（洋輔 × 天真）の自社プロダクト。GOOD ORDER と同じ GOODシリーズ。

来店客が卓上POPのQRを読み、5段階評価に答える。
★4〜5 は AI が書いたクチコミ下書きをコピーして Google マップへ、
★1〜3 は店内向けの改善アンケートへ分岐する（低評価を公開レビューに出さない）。

| 状況 | 結果 |
|---|---|
| キーが台帳に無い | **落とす**（新しい種類の違反） |
| キーがあり、今回の件数 ≤ 台帳の件数 | 通す |
| キーがあり、今回の件数 > 台帳の件数 | **落とす**。「1件で登録されていたものが2件に増えています（+1）」と出す |
| キーがあり、今回の件数 < 台帳の件数 | 通す。「返済が進んだもの」として報告する |

- 旧形式（キーの配列）が置かれていたら、黙って読み替えずエラーで落とす。
  件数を持たない台帳を「全部1件ずつ」と誤解すると、いきなり大量に落ちるため
- `--update-baseline` は**資産の質（soft）だけ**を書き出す。構造違反は原理的に混入しない。

## 2026-08-05（5回目） — 5画面すべてで下に空白ができるバグと、検証体制の作り直し

天真から「ボタンがくっついている・844pxで指定したのに下に空白ができる」という強い指摘。
01・02・04で発生し、03・06は無事だった。

### 原因：`min-height` は子要素の `height: 100%` の基準にならない

`app/r/[storeSlug]/page.tsx` の外枠は `min-h-dvh`（最小の高さ）。各画面コンポーネントは
`size-full`（`width: 100%; height: 100%`）で外枠いっぱいに広がるつもりで書いていたが、
**CSSの仕様上、`min-height` だけでは子のパーセント指定の基準にならない**
（子から見ると「高さが未確定の親」のまま）。結果、各画面は中身の高さぶんしか描画されず、
`min-h-dvh` が保証する残りの高さは、透明な外枠の中に空白として残っていた。

03（下書き結果）・06（サンクス）は `justify-center` 等の別レイアウトで、たまたま症状が
目立たなかっただけで、同じ構造上の欠陥を抱えていた。

**修正：`size-full` → `w-full flex-1` に変更**（01/02/03/04/06 全画面）。
外枠は `flex flex-col` なので、`flex-1` は「残りの高さを実際に埋める」という正しい指示になる。
`min-height` の値に関わらず、コンテンツが多いときは自然に外枠ごと伸びてスクロールできる
（2-1a のルールとも矛盾しない）。

### 検証体制：ブラウザ自動化をやめ、Playwrightのヘッドレスブラウザに切り替えた

天真の実ブラウザ（`claude-in-chrome`）を使った検証が、繰り返しウィンドウを出現・リサイズさせて
迷惑をかけていた。「別プロファイルに繋ぐ」提案も、Googleアカウントの切替とChromeプロファイル・
拡張機能の接続を混同しており、実際には機能していなかった。

**`playwright` を devDependency に追加した。** 天真の環境には一切触れない、完全ヘッドレスの
Chromiumで検証する。ブラウザバイナリは既にマシンにキャッシュ済みだったため追加ダウンロードは無かった。
`npm run check` には含めない（画面確認用のツールであり、機械的な合否判定の対象ではないため）。

今回は一時ファイル（プロジェクト直下に置かないと `node_modules` を解決できないため）で検証し、
使用後に削除した。**今後スクリーンショット検証が要るときは、同じ手法（Playwright・完全ヘッドレス）
を使うこと。天真のブラウザには触れない。**

### 副産物：devサーバーのプロセスが1時間以上再起動されずに残っていた事故

`.next` を削除しても、**動いている node プロセス自体は再起動しないと直らない**
（メモリ上に壊れたモジュール参照を持ったまま）。天真が別ターミナルで `npm run dev` を
実行しても、ポート3001で動いていた古いプロセス（PID 60093）は生き残ったままで、
何度再起動指示をしても同じエラーが再現し続けた。最終的にそのPIDを直接 `kill` して解消した。

**教訓：「devサーバーを再起動してください」と頼むだけでなく、`lsof` でポートを掴んでいる
プロセスのPID・起動からの経過時間を実測して、本当に再起動されたか確認すること。**
`npm run dev` を実行した「つもり」でも、別のターミナル・別プロセスが残っていることがある。

なお、この作業中にGOOD ORDER側のdevサーバーが停止したらしく、GOOD LOOPが
ポート3000を取得できるようになった（以降 `http://localhost:3000/r/...` が入口）。

### 追記：`npm install` をdevサーバー起動中に実行すると同じ壊れ方を再現する

`playwright` を追加インストール（`npm install -D playwright`）した直後、devサーバーが
起動していたまま（PID自体は新しいプロセスだった＝ゾンビではない）だったにもかかわらず、
同じ「Cannot find module './xxx.js'」エラーが再発した。`node_modules` の変更をdevサーバーの
ファイル監視が拾って `.next` のキャッシュと矛盾した状態になった、と考えられる。

**教訓：`npm install`（追加・削除どちらも）はdevサーバーを止めてから行うのが安全。**
止めずに行った場合は、`.next` 削除＋devサーバー再起動が必要になると想定しておくこと。
